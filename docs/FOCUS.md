# Фокус работы и план (с 22.10.2026)

Этот документ задаёт, на чём сосредоточены диплом и статья. Он уточняет `docs/PRODUCT_PLAN.md`:
- правила владельца из `docs/NEXT_PLAN.md` (раздел 0) и `docs/CLOUD_AGENT_PROMPT.md` остаются в силе;
- при расхождении с другими планами решает этот документ.

## 1. Цель

**Ускорить выполнение UVM-тестов функциональной верификации на гибридной системе «ПЛИС + ARM»** — для
процессорных ядер и больших IP-блоков. По словам научного руководителя, большие IP в тестировании занимают
даже больше времени, чем процессорные ядра.
- **«Без доработок» (решено с научным руководителем, 24.10.2026)** — это UVM-тест, написанный по нашим
  правилам и наследующий наши базовые классы. Такой тест идёт и в симуляции на ПК, и на плате без единой
  правки.
- **Основа — DUT и подключённые к нему интерфейсы; драйвер наследуется от нашего класса** (так предложил
  научный руководитель). Ограничения на тест задаются контрактом:
  - драйверы, мониторы и транзакции наследуются от универсальных классов `uvm/ocv_uvm_pkg.sv`. Они одни
    на все случаи и от теста к тесту не правятся;
  - с DUT тест общается только через SV-интерфейсы, подключённые к его выводам. Из них же генерируется
    обёртка DUT для ПЛИС;
  - правила — в шапке пакета: с DUT только через агенты; выводы только в `drive()`/`sample()`; без
    привязки к номеру такта; конец теста по транзакциям.
- **Метрики покрытия сохраняются:** покрытие RTL считается в ПЛИС, функциональное — на ARM (раздел 3а).
- **Существующие тестбенчи, написанные без нас** (core-v-verif), — через адаптер `uvm2board.py`, который
  подставляет те же базовые классы через фабрику. Это дополнительная демонстрация, не главный результат.

Цель совпадает с защищённой темой ВКР (слайды 14.10.2026): объект — процесс функциональной верификации
с помощью UVM-тестов, предмет — методы их исполнения на гибридной системе. Название не меняется.

**Тезис статьи:**

> UVM-тест процессорного ядра или большого IP-блока, написанный по контракту (наследование от универсальных
> базовых классов), без правок выполняется и в симуляции, и на недорогой плате «ПЛИС + ARM»: длинная
> регрессия, которая на ПК идёт часами, на плате занимает минуты; покрытие RTL считается в ПЛИС,
> функциональное — на ARM. Выигрыш определяется числом тактов DUT на транзакцию теста.

## 2. Мерило: выигрыш в часах, а не в секундах

- **Считаются только длинные тесты.** На ПК (чистый UVM в Verilator) они идут часы и дольше, на плате —
  минуты.
- **Главные метрики:**
  - время до первой ошибки на длинной регрессии;
  - время одного длинного теста.
- Короткие тесты (hello, dhrystone, coremark — секунды и минуты на ПК) — только проверка, что путь работает.
  В главную таблицу они не идут.
- **ПК для сравнения** — ноутбук владельца (Core Ultra 7 155H, одно P-ядро), как во всех прежних замерах.
  Облачные машины для эталонных цифр не годятся.
- Прогон на ПК длиннее 10 ч можно оценить по измеренной скорости. Такая цифра помечается как оценка, и
  рядом приводится скорость, на которой она основана.

Ориентиры скорости:
- чистый UVM core-v-verif на ПК — около 1,2–1,5 тыс. команд/с (coremark, 2,79 млн команд, за 1856–2257 с);
- 1 ч на ПК — около 5 млн команд, сутки — около 120 млн.

## 2а. Граница метода: такты DUT на транзакцию

Граница проходит не между IP и процессорами, а по числу тактов DUT на одну транзакцию теста:
- **на ПК** время растёт с числом тактов и с размером схемы: Verilator на большой схеме медленнее за такт;
- **на плате** такт DUT почти бесплатен (ПЛИС — десятки МГц), а время определяет число транзакций, которые
  обрабатывает ARM: `randomize()`, передача, scoreboard.

| DUT | тактов на транзакцию | выигрыш платы |
|---|---:|---:|
| mac16 (малый IP, операция за такт) | 1 | ×0,5 — худший случай |
| SHA-256 (блок 512 бит) | ~65 | ×5 |
| SCR1 с моделью (тест почти не вмешивается) | — | ×76 |
| большой IP (план 4.9) | тысячи | ожидается больше всего |

Итог: малые IP с короткими транзакциями — ПК; большие IP и процессоры — плата. Кривая «выигрыш от тактов
на транзакцию» — план 4.10, главный график статьи о том, когда плата выгодна.

## 3. Что входит в работу и как

| часть | роль для цели | в статье |
|---|---|---|
| контракт: базовые классы и правила (`uvm/ocv_uvm_pkg.sv`) | основа переноса без доработок | главный вклад |
| хаб и обёртка ядра (`hw/rtl`, `hw/cpu`, `.bind`) | ядро подключается без ручной правки RTL | архитектура |
| эталон на A72 (JIT), сверка подписями окон | без них UVM-тест на ARM не ускоряется | средство; сравнение с DiffTest-H |
| адаптер для существующих тестбенчей (`uvm2board.py`, `tbparse.py`, `uvm_fast`) | чужой тест без нашего контракта | дополнительно |
| контрольная точка → VCD на ПК (`tools/ckpt_replay.sh`) | ошибку с платы можно отладить | кратко |
| функциональное покрытие по отобранным записям (`docs/COVERAGE.md`, 2.3) | исходные covergroup на ARM | вероятная новизна |
| покрытие RTL в ПЛИС (план 4.8) | метрика кода без потери скорости | да, если успеем |
| тест 2 (CVA6 без UVM, `minstreth` ×95) | довод «работает и на большом ядре» | вспомогательно; не выдавать за UVM-результат |
| большой IP-блок с тестом по контракту (план 4.9) | второй показательный пример, рядом с CVA6 | да |
| малые IP (mac16 ×0,5, SHA-256 ×5) | точки кривой «выигрыш от тактов на транзакцию» | да, на графике (4.10) |

## 3а. Покрытие

| вид | где | статус |
|---|---|---|
| покрытие кода RTL (ветви, переходы автоматов; toggle — позже) | ПЛИС: счётчики, которые вставляет инструмент; ARM читает их в конце прогона | нет, план 4.8 |
| функциональное по транзакциям (covergroup теста, isacov) | ARM, исходные covergroup; при нехватке скорости — с фильтром записей | есть, точность проверена на ПК; на плате — 4.4 |
| функциональное по внутренним сигналам каждый такт | не делаем; редко меняющиеся сигналы — поток `watch` | в ограничения |

«RTL без изменений» уточняется: RTL автора не правится руками. Счётчики покрытия инструмент вставляет
автоматически, и только в сборку для ПЛИС.

## 4. План

### 4.1. UVM-тест процессорного ядра по контракту и длинный сценарий для него — без платы

- **Тест.** UVM-тестбенч ядра по нашим правилам:
  - агенты и транзакции наследуют `ocv_uvm_pkg`;
  - scoreboard сверяет с эталонной моделью через DPI (`ocv_checker`);
  - функциональное покрытие — covergroup isacov из core-v-verif на транзакциях монитора.

  Образец — `examples/scr1/uvm`, но без ручного `scr1.json` (см. 4.7).
- **Ядро — CVA6, рекомендация.** Внесённая ошибка `minstreth` (перенос после 2³² команд) и программа
  nettle-aes ×1100 уже есть. Образ ПЛИС на 50 МГц собран, без UVM на ПК известно 8,3 ч. Запасной вариант —
  CV32E40P.
- **Готово, когда:**
  - тест без правок идёт в симуляции на ПК и в режиме платы на ПК (ПЛИС смоделирована);
  - на исправном ядре — PASS;
  - на ядре с ошибкой ошибка найдена.

**Устройство (24.10, перед реализацией):**
- **DUT** — обёртка CVA6 из `hw/cpu` (`gen/cpu_wrap.py` по `examples/cva6/cva6.bind`), та же, что в образе ПЛИС
  `BOOT_cva6.BIN`: образ пересобирать не нужно.
- **Интерфейс** — её выводы: 11 каналов.
  - выходные: `issue`, `regw`, `store`, `irq`, `csrr`, `proto`, `dev_req`;
  - входные: `program`, `dev_resp`, `in_irq_i`, `cfg_lat`.
- **Тест по контракту** (как `examples/scr1/uvm_c`):
  - на канал — транзакция от `ocv_item` и драйвер или монитор;
  - последовательность загрузки программы;
  - ответы периферии — последовательность по `dev_req` (на nettle-aes это единицы обращений);
  - covergroup isacov — на транзакциях монитора `issue`.
- **Scoreboard** — `ocv_checker` на каждый выходной канал с C-эталоном.
  - На плате записи сверяются в C прямо на выходе из ПЛИС, без UVM-объекта на команду. Так сохраняется
    скорость прогонщика (14,3 млн команд/с в тесте 2).
  - Чтения счётчиков — шаблоны разрыва окна (`OCV_UVM_CHECKER_BRK`).
- **Нужно сделать в C:** переходник «одна модель CVA6 (`models/cpu/ocv_cpu_model.c`, jit) → очереди
  ожидаемых записей по каналам». Функция канала берёт запись из своей очереди и продвигает модель, пока
  очередь пуста. Сейчас каждый канал проверяется своей независимой функцией, а модель ядра одна на всех.

**Статус 4.1 (24.10): готово на ПК.**
- **Тест** `examples/cva6/uvm_c`: 11 каналов обёртки; транзакция и драйвер или монитор на канал;
  последовательности:
  - загрузка программы;
  - расписание прерываний и задержки памяти — входы ядра, которые подаёт тест;
  - ответчик периферии.

  Scoreboard — `ocv_model_checker`; тест ничего к нему не подключает.
- **Симуляция** (RTL CVA6, Verilator): `minstret` — 300 094 записи сверены моделью, 0 расхождений; на RTL с
  внесённой ошибкой `minstreth` — `MISMATCH regw record 20: dut 0, model 1`.
- **Форма для платы на ПК** (ПЛИС смоделирована, сверку ведёт ядро прогонщика; стимул — от драйверов теста,
  обращения к периферии — в его агенты): PASS, `issue=200045 regw=100030 store=1 csrr=17 dev_req=1` — те же
  числа, что у прогонщика на настоящей плате.
- **Как устроено:**
  - `uvm/ocv_uvm_model.c` — модель в симуляции: свой поток, переплетённый режим;
  - `uvm/ocv_uvm_runner.c` — сторона платы: «эстафета» с ядром прогонщика;
  - `ocv_contract.py --desc` — описание ядра от его обёртки, тест проверяется на соответствие ему. Хаб — тот
    же, что в образе ПЛИС (`DUT_ID 0x3772f7cb`).
- **Скорость на ПК** (этот ноутбук, одно ядро, 24.10): nettle-aes ×1 — 8 078 334 записи сверены за 301 с, память
  ровная, 149 МБ; это ~13,5 тыс. команд/с. Тот же тест на nettle-aes ×1100 (4,48 млрд команд, ошибка `minstreth`)
  — **около 92 ч на ПК** (оценка по этой скорости). На плате тот же прогон прогонщиком: окно за 5 мин, точная
  запись за 55 мин (4.4).
- **Осталось:**
  - тот же тест на плате (сборка aarch64 готова к дню с платой);
  - длинный сценарий nettle-aes ×1100 с ошибкой;
  - covergroup isacov на транзакциях `issue`: на плате их нет, через фильтр записей (2.5).

### 4.2. Путь UVM-теста выдерживает миллиарды команд — без платы

- Проверить потоковое сравнение (`stream_compare`) на пути UVM-теста. В 1б без него прогонщик
  падал по нехватке памяти через 15 с.
- 64-битный счётчик записей хаба `taken` — пересборка образов (Vivado, у владельца).
- **Готово, когда** длинный прогон в режиме платы на ПК идёт с постоянной памятью, а номера записей больше
  2³² считаются верно.

### 4.3. Эталон на ПК — у владельца

- Тот же длинный UVM-тест (4.1) в симуляции, Verilator на ноутбуке.
- Один настоящий прогон 8–10 ч либо замер скорости за несколько часов и оценка.
- **Готово, когда** есть время до ошибки на ПК (измеренное или оценка с её основанием).

### 4.4. День с платой

1. Короткая проверка: `docs/BOARD_DAY.md` — hello, coremark, SCR1, CVA6; попутно тест 1 core-v-verif через
   адаптер.
2. **Длинный прогон с внесённой ошибкой:** время до ошибки, пропускная способность, 0 ложных
   расхождений на исправном ядре.
3. Попутно — цена фильтра покрытия на A72 (`OCV_BENCH_ARCH=aarch64`). По ней решается этап 2.5:
   - если цена приемлема — фильтр в jit;
   - если нет — на плате только отбор записей, covergroup на ПК.
- **Готово, когда** в главной таблице есть строка «UVM-тест верификатора, время до ошибки: ПК — часы, плата —
  минуты».

**Сделано 24.10 (плата, CVA6 без UVM — тест 2, не UVM-результат):**
- **Исправное ядро, nettle-aes ×1100.** 4,48 млрд команд сверено, PASS, 0 ложных расхождений, 314 с
  (14,3 млн команд/с). Прогонщик с потоковым сравнением, память ровная.
- **Внесённая ошибка `minstreth`.** Окно найдено за 319 с. Повтор до точной записи с окном 1 идёт от
  начала программы: 36+ мин без OOM, до конца не доведён (см. PRODUCT_PLAN 4г).
- **Короткие программы** (hello, dhrystone, coremark) и сгенерированные тесты jit/fast: PASS.
- **Два расхождения на исправном ядре** (`gen=directed lat=2,3` и `gen=random seed=7`: `issue`, поле `pc`):
  - повторяются на ПК в Verilator — это расхождение ядра и модели, а не ложное расхождение платы;
  - место одно: в обработчике ловушки ядро идёт на `0x1b4`, модель ждёт `0x1b0` (`addi t4,t4,2` перед
    `csrw mepc`);
  - на старом прогонщике было то же самое. Причину ещё не разбирали.
- **Цена фильтра покрытия на A72:** 5,0 мкс на команду против 575 нс без записей (`docs/COVERAGE.md`). В
  нынешнем виде на плату не годится: нужен уровень 1 в jit (2.5).
- **Найдено и исправлено:** генератор программ давал на A72 другую программу, чем на ПК, при одном seed
  (порядок вычисления аргументов). Теперь программы одинаковые, проверено по подписи на плате.

### 4.5. Незнакомое ядро без ручной работы (усиливает «без доработок»)

- Ibex или PicoRV32 — скачивание в `ext/` с разрешения владельца.
- Записать каждый ручной шаг. Цель — ноль шагов, кроме выбора файлов.
- **Готово, когда** новое ядро проходит регрессию в режиме платы на ПК без правок нашего кода под него.

- Документ для научного руководителя: лид и выводы под цель из раздела 1, FERIVer в литературе.
- Слайды 3 и 5: источник цифр 7,8 МГц / 4 кГц (это DiffTest-H, XiangShan); «миллиарды», а не «миллионы»

### 4.7. Упаковка транзакции по умолчанию — без платы

- Сейчас `to_rec()`/`from_rec()` в `ocv_item` объявлены как `pure virtual`, и их генерирует скрипт по
  описанию (`scr1.json`). Нужна упаковка по умолчанию в базовом классе по полям транзакции:
  - стандартный `pack`/`unpack` UVM по полям `uvm_field_*`, если `uvm_packer` работает в нашем Verilator
    на A72 и не слишком медленный;
  - иначе — генерация по классу транзакции.
- Обёртка ядра для ПЛИС — из того же SV-интерфейса.
- **Готово, когда** тест из 4.1 собирается без ручного описания схемы: только интерфейс, классы теста и
  RTL.

### 4.8. Покрытие RTL в ПЛИС, минимальный вариант — после 4.4

- **Одно ядро** — SCR1 или CV32E40P, без CVA6.
- **Метрики:** ветви и переходы автоматов.
- **Инструмент** вставляет синтезируемые счётчики в сборку для ПЛИС: Yosys; для SystemVerilog — sv2v
  или Synlig. ARM читает счётчики в конце прогона.
- **Опора:** Under Cover, ZynqParrot, DifuzzRTL.
- **Готово, когда:**
  - на одном тесте покрытие из ПЛИС совпадает с покрытием Verilator на ПК;
  - расход ресурсов ПЛИС измерен.

### 4.9. Большой IP-блок — тест по контракту и длинный сценарий

- **Выбор кандидата.** Требования:
  - открытый RTL и подходящая лицензия;
  - помещается в ПЛИС VD100 (VE2302 небольшая — проверить по ресурсам);
  - есть эталон на C для scoreboard: для криптографии и сжатия просто, для кодеков сложнее;
  - на ПК длинный тест идёт часами;
  - тысячи тактов DUT на транзакцию.

  Кандидаты проверить: IP-блоки OpenTitan (AES, KMAC/SHA-3, OTBN — у них есть свои UVM-окружения, это
  ориентир для времени на ПК), открытые FFT и JPEG-кодеры. Скачивание в `ext/` — с разрешения владельца.
- **Тест** — по контракту, как в 4.1: агенты от `ocv_uvm_pkg`, упаковка по умолчанию (4.7), эталон на C
  через DPI, covergroup на транзакциях.
- **Внесённая ошибка**, которая проявляется на длинном сценарии.
- **Готово, когда:**
  - тест без правок идёт в симуляции и в режиме платы на ПК;
  - на плате есть время одного длинного теста и время до ошибки против ПК — в часах.

### 4.10. Кривая «выигрыш от тактов на транзакцию»

- **Точки:** mac16 (1 такт), SHA-256 (~65), большой IP (4.9), CVA6 (4.1). Все тесты — по контракту.
- Для одного IP по возможности меняем длину транзакции (размер блока или пакета), чтобы увидеть ход
  кривой на одном DUT.
- **Готово, когда** есть график и простая модель:
  - время на ПК ≈ такты × цена такта (зависит от размера схемы);
  - время на плате ≈ max(транзакции × цена на ARM, такты / частота ПЛИС).

### 4.11. Крупные ядра и IP (25.10, владелец: «более крутые ядра», вариант «в»): сначала cv64a6, затем OTBN

**cv64a6** — 64-битный CVA6 (`cv64a6_imafdc_sv39`, плавающая точка выключена, как B и Zcb у cv32a60x). Ресурсы
есть: весь образ с cv32a60x — 22,7 тыс. LUT из 150 тыс. (сам CVA6 — 10,5 тыс.). Работа — перевод цепочки с RV32 на
ширину XLEN:
1. **RTL.** `examples/cva6_64`: обёртка ядра с RVFI шириной XLEN, биндинг с другой `TARGET_CFG`; разбор в Verilator.
2. **Обёртка** (`gen/cpu_wrap.py`): директива `xlen 64` — ширины полей потоков (pc, данные, адреса, маска записи
   8 байт); загрузчик программы и память AXI (данные уже 64 бита).
3. **Эталон.** `cpu_model.h` и `ocv_cpu_model.c` — значения и адреса шириной XLEN; эталон для RV64 — Spike
   (`cpu_spike.cc`, `cpu=spike`). Быстрые `fast`/jit остаются RV32: для RV64 это ошибка, а не тихий медленный путь.
4. **Программы и ошибка.** Embench (nettle-aes) и направленные тесты под rv64 (`riscv-none-elf-gcc`). Внесённая
   ошибка для RV64 — своя: у RV64 нет `minstreth`.
5. **Тест по контракту** (как `examples/cva6/uvm_c`): симуляция и форма платы на ПК; на плате — образ ПЛИС
   (Vivado, у владельца) и Spike для aarch64 (`tools/get_spike.sh aarch64`).
6. **Скорость на плате:** замер Spike на A72. RV64-jit — отдельным решением по этому замеру.

**Статус (25.10), на ПК:** шаги 1–3 и симуляция шага 5 готовы.
- `rv64_basic`: 16 244 записи, 0 расхождений.
- `minstret64` (ловушки, перенос в бит 32, переполнение 64 бит): 300 098 записей, 0 расхождений.
- Embench nettle-aes ×1 под rv64 (`CV_SW_MARCH=rv64imac_zicsr_zifencei CV_SW_MABI=lp64 tools/embench.sh`):
  9 238 542 записи за 247 с, 0 расхождений.
- Найдено по дороге: cv64a6 исполняет только окно отладки 0–0xfff, ROM и DRAM с 0x8000_0000 — в обёртке
  исполняемой стала вся RAM.
- **Внесённая ошибка для RV64** — та же строка, что у RV32 (`build/fault_instret/cva6`: потерян перенос
  `instret[31:0]` → `[63:32]`); на RV64 она видна в чтении 64-битного `minstret`. Для этого Spike с профилем
  `:cva6` сверяет `minstret` точно (прежде значение бралось у ядра — ошибку не было видно). `minstret64` на
  ядре с ошибкой: MISMATCH на записи 20 (перенос в бит 32) и 24 (переполнение 64 бит); исправное — 0.
- Длинный сценарий: nettle-aes ×1100 с чтением `minstret` (`EMBENCH_BOARD=embench_board_instret`, rv64).
- Форма платы на ПК (`run.sh host`): `rv64_basic` и `minstret64` — PASS (`minstret64`: issue=200052, regw=100033,
  csrr=15). Исправлено в `gen/cpu_wrap.py`: `stop ... retire` сравнивал адрес потока store (у RV64 он выровнен по
  8 байт) с регистром конца по 4 байта — конец не наступал; теперь слово XLEN/8 и его байты (для RV32 вывод тот же).
- Сборка для платы: Spike для aarch64 (`tools/get_spike.sh aarch64`, 2,5 мин) и `build/uvm/cva6_64_c_aarch64/tb_top`
  (статический, 26 мин сборки). **Ждёт:** образ ПЛИС cv64a6 (Vivado, владелец:
  `hw/cpu/run.sh examples/cva6_64/cva6_64.bind vd100` с `OCV_GEN_FLAGS="--dma 128"`; с ошибкой — `CVA6=build/fault_instret/cva6`),
  затем на плате: `minstret64`, nettle-aes ×1100 (`build/embench/rv64/nettle-aes_s1100_instret_rv64.hex`) на обоих
  образах, скорость Spike на A72 (шаг 6).
- Ограничение: один порт фиксации (у cv64a6 их два).

**OTBN** (OpenTitan, `ext/opentitan/hw/ip/otbn`) — после cv64a6: ускоритель больших чисел со своей программой,
тысячи и миллионы тактов на операцию (RSA, ECDSA), свой UVM-тестбенч у OpenTitan — ориентир времени на ПК.

**OTBN — план (25.10).** Программа — ML-DSA-87 из OpenTitan (`sw/otbn/crypto/mldsa87`): подпись — 1,06 млн тактов,
648 тыс. команд (`otbnsim`, вектор NIST ACVP #61 — PASS за 57 с на Python); 64 % тактов OTBN ждёт KMAC.
1. **DUT** — OTBN вместе с KMAC, как в Earl Grey (`examples/otbn/otbn_kmac_ocv.sv`): без KMAC ML-DSA не работает
   (в `otbn_top_sim` OpenTitan его нет). Наружу — одна шина запрос/ответ (бит 16 адреса выбирает блок, у каждого
   свой TL-UL host-адаптер); EDN и ключ OTP — детерминированные (от них зависят маскирование и скремблирование,
   не результаты). Файлы — FuseSoC OpenTitan (`examples/otbn/files.sh`, `build/otbn_venv`). Lint Verilator — чисто.
2. **Программы** — ассемблер/линкер OpenTitan (`otbn_as.py`, `otbn_ld.py`, xpack `riscv-none-elf`), ELF → слова
   IMEM/DMEM для теста.
3. **Тест по контракту:** шина (запись/чтение, ожидание простоя OTBN — запрос, который DUT принимает, когда OTBN
   свободен), настройка KMAC как `kmac_hwip_default_configure`, загрузка программы, по кругу: keygen из случайного
   xi → чтение pk; sign случайного μ → чтение подписи.
4. **Эталон** — mldsa-native (`ext/mldsa-native`, Apache 2.0/MIT/ISC): `keypair_internal(xi)`,
   `signature_internal(μ, externalmu=1, rnd)`. Модель не разбирает маскированный секретный ключ: keygen OTBN
   кладёт его прямо туда, откуда читает sign, а модель считает тот же ключ из xi. Проверено: xi = share0 XOR share1,
   pk_rho и t1 вектора ACVP #51 совпадают.
5. На ПК для локализации найденной ошибки — `otbnsim` (как у OpenTitan).

**Статус OTBN (26.10), симуляция на ПК** (`examples/otbn/uvm_c/run.sh pc`, `build_prog.sh`):
- 2 раунда keygen + sign со случайными xi и μ: 19 573 ответа шины, 0 расхождений с mldsa-native (pk — 648 слов,
  подпись — 1 157 слов за раунд). Раунд — 2,05 млн тактов (keygen 0,97 млн, sign 1,06 млн), на ПК ≈ 2 мин 20 с
  (≈14 тыс. тактов/с; Verilator с флагами CVA6). На плате при 50 МГц ≈ 41 мс работы ПЛИС на раунд.
- Каждый раунд начинается с образа DMEM приложения (как `otbn_load_app`): sign затирает то, с чего начинает keygen.
- Найдено и исправлено в `ocv_model_checker`: «тишина» DUT (100 мкс без записей) объявлялась посреди 10-мс
  операции — теперь только когда ни один драйвер не ждёт ready; `finish()` — тест говорит, что стимулы кончились,
  и ждёт сверки до последней записи (`done` бывает и между двумя транзакциями); переполнение в проверке кольца
  `ocv_uvm_model.c`.
- Форма платы на ПК (`run.sh host`): раунд — PASS, 13 623 стимула, 13 620 ответов сверено, 2,12 млн тактов DUT.
  Поправлено: раннер в форме платы идёт столько пакетов, сколько стимулов шлёт тестбенч (`--batches` без предела);
  `--max-polls 0` — без предела (как `--stall-polls 0`); тест OTBN задаёт их сам (`chk.run_args`); модель ПЛИС
  в программе получает пустые аргументы (RTL OpenTitan читает plusargs).
- Внесённая ошибка (`examples/otbn/fault/otbn_mod_result_selector.sv`, `OCV_RTL_REPLACE`): модульное сложение 32-битных
  элементов, у результата которого (a + b − q) младшие K бит нулевые, даёт его с инвертированным битом 0 — раз
  на ≈2^K редукций (`+define+OCV_OTBN_FAULT_BITS=K`). K = 18: поймана в первом раунде (pk_t1, запись 11 933).
  Первая версия (a + b = q → q вместо 0) за 10 раундов не проявилась: редкость и q ≡ 0 по модулю q.
- K = 22 (30 раундов на ПК): поймана в 5-м раунде, в подписи (`sig_c_tilde`, ответ 36 275), на 136,5 мс модельного
  времени = 13,65 млн тактов — на ПК ≈ 16 мин (142 мкс/с); на плате при 50 МГц — 0,27 с работы ПЛИС.
  Y < q < 2^23: K ≥ 23 — это Y = 0 (вдвое реже K = 22); для ошибки «на часы» нужно условие реже.
- Сборка для A72: `build/uvm/otbn_c_aarch64/tb_top` (статический). На плату ещё нужны
  `build/otbn/prog/run_mldsa87.{load,sym}` (тест и модель читают их по +PROG).
- **Синтез (26.10, `OCV_STOP=synth examples/otbn/fpga.sh`, 91 мин):** влезает. DUT — 112 852 LUT (OTBN 84 360,
  KMAC 28 489), 31 810 регистров, 13 RAMB36 + 8 RAMB18, 16 DSP; весь образ — 116 183 из 150 272 LUT (77 %).
  Втрое больше CVA6 (10,5 тыс. LUT). 0 ошибок, 0 критических предупреждений.
- **Реализация на 50 МГц (98 мин):** LUT DUT 102 884, образа 106 153; **WNS −0,001 нс** (11 путей внутри OTBN:
  предекодер → 256-битный сумматор → регистровый файл, 59–61 уровень логики) — тайминг не закрыт, образ не
  берём (`build/vd100/otbn_50mhz_wns-0.001`). Пересборка на 45 МГц (`OCV_CLK_MHZ=45`): частота, на которой
  закрывается DUT, не разгон; выигрыш платы меньше на 10 %.
- **Ждёт:** образ ПЛИС OTBN+KMAC — `examples/otbn/fpga.sh` (примитивы
  `prim_xilinx_ultrascale`, 50 МГц, `--dma 128`): сначала `OCV_STOP=synth examples/otbn/fpga.sh` — влезет ли в
  VE2302; затем исправный и `OCV_OTBN_FAULT_BITS=22 examples/otbn/fpga.sh`.

## 5. Чего не делаем

- Не ускоряем короткие тесты и тест A: выигрыш в секундах статье не нужен.
- Не берём малые IP с короткими транзакциями как показательный пример: там ПК быстрее (mac16 ×0,5). Они
  нужны только как точки кривой (4.10).
- Не соревнуемся с ENCORE, DiffTest-H и Lyra в мегагерцах.
- Не делаем функциональное покрытие по внутренним сигналам каждый такт (синтезируемые covergroup) — это
  в ограничения.
- **Новое направление только с согласия владельца:** второе ядро A72, копии DUT, частота ПЛИС, перенос
  тестбенча CVA6 целиком.

## 6. Риски

- **Чужой тестбенч может упереться в скорость ARM.** Это пробуждения процессов UVM; вариант E1 на плате медленнее ПК.
  Тест 1 (`uvm_fast`) обходит это: до тестбенча доходят только обращения к периферии. Но на длинных
  программах это ещё не проверено.
- **Фильтр покрытия не насыщается.** Записей остаётся примерно столько, сколько корень из длины теста. Для
  статьи достаточно точности, скорость фильтра — в ограничения. Улучшение: брать группу команды у
  тестбенча (`get_instr_group`).
- **Плата одна, ядра малые (RV32).** Это пишется в ограничения прямо.
- **Большой IP может не поместиться в VE2302.** Кандидата выбираем по ресурсам заранее, до того как писать
  тест.
- **Эталон на C для IP** нужно взять готовый (OpenSSL, эталонные реализации стандартов), а не писать самим.
