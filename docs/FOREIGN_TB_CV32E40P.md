# Этап 4: чужой тестбенч — core-v-verif, CV32E40P

Исходники: `core-v-verif` (OpenHW, ветка master, клон без истории) и `cv32e40p` на хеше `fcd5968`,
указанном в `cv32e40p/sim/ExternalRepos.mk`. Лежат в `pvo_scr1/ext/` (не в git). Тестбенч не правится.

## Из чего состоит тестбенч (опись)

| часть | что делает | как устроена | на плату |
|---|---|---|---|
| `uvmt_cv32e40p_dut_wrap` | обёртка ядра | модуль тестбенча; порты — SV-интерфейсы (OBI команд и данных, прерывания, отладка, управление ядром) | ядро в ПЛИС; граница DUT — порты `cv32e40p_wrapper` |
| `uvma_clknrst` | такт и сброс | драйвер UVM сам генерирует такт (`vif.clk = ...` с задержками) | такт — в ПЛИС; сброс — из последовательности |
| `uvma_obi_memory` ×2 | память команд и данных | реактивный слейв: монитор видит запрос, последовательность читает модель памяти UVM (`uvml_mem`) или виртуальную периферию, драйвер отвечает со случайными задержками gnt/rvalid | как есть — ARM отвечает на каждую выборку (ядро ждёт); быстро — память в ПЛИС, на ARM только адреса периферии |
| виртуальная периферия (18 последовательностей) | печать, счётчик тактов, статус теста, таймер прерываний, управление отладкой, случайные числа | последовательности по адресам `0x1000_0000`, `0x1500_xxxx` | на ARM (редкие обращения) |
| `uvma_interrupt` | прерывания | драйвер выставляет `irq` по последовательности (случайные времена) | входной канал |
| `uvma_debug` | запрос отладки | драйвер `debug_req` | входной канал |
| scoreboard `uvme_cv32e40p_sb` | — | пуст (`create_sbs` ничего не создаёт) | — |
| step-and-compare + `iss_wrap` | сверка с эталоном по каждой команде | модуль `CPU` Imperas (коммерческий, DPI `svimp_*`), сигналы ядра берутся иерархическими ссылками (`tracer_i.retire`, `register_file_i.mem`) | Imperas недоступен; включается `+USE_ISS` (по умолчанию в Makefile — да) |
| SVA: `interrupt_assert` (22), `debug_assert` (29), OBI-ассерты (bind) | свойства протокола и ядра | `bind` внутрь ядра и обёртки, иерархические ссылки | в ARM не переносятся: нужны сигналы каждого такта внутри ядра |
| покрытие (`uvme_*_cov`, `isa_covg_if`) | функциональное покрытие | от монитора прерываний и от сигналов ISS | вслед за источником |
| признак конца теста | `vp_status_if.tests_passed/failed/exit_valid` | пишет программа через виртуальную периферию | на ARM |

Без Imperas тест проверяет себя сам: программа (riscv-tests, corev-dv и т.п.) пишет «пройден/не
пройден» в виртуальную периферию. Сверки по каждой команде в открытой части тестбенча нет.

## Что из этого следует

1. Сборка. Наш путь на плату и эталон «Verilator на ПК» требуют, чтобы Verilator собрал этот
   тестбенч. Официально core-v-verif поддерживает Verilator только для простого тестбенча `tb/core`
   (не UVM). Сделано — см. ниже: 4 исправления в Verilator, компонент ISS без ISS.
2. Разбор. `uvm2board.py` сейчас ждёт один экземпляр ядра в вершине, такт `always #N clk = ~clk`,
   драйвер «valid/ready». Здесь — обёртка с интерфейсами-портами, такт из UVM-драйвера, реактивные
   слейвы. Первый барьер (ширины через параметры и `` `define ``) снят в `tbparse.py`.
3. Скорость. Как есть: каждая выборка команды — транзакция UVM на ARM, ядро ждёт ответа
   (~десятки мкс на команду). Выигрыш даёт перенос памяти OBI в ПЛИС с той же моделью поведения
   (содержимое — из `fw_preload`, задержки gnt/rvalid — по тем же настройкам `cfg`), обращения
   к виртуальной периферии — на ARM.
4. Проверка. Самопроверка программы сохраняется как есть. Сверка по каждой команде — только если
   подключить свою модель (Spike) вместо Imperas, а это уже добавление к тестбенчу.

## Сборка Verilator'ом (без правки тестбенча)

`examples/cv32e40p/vlt.sh lint|build|run` берёт списки файлов core-v-verif как есть. Что понадобилось:

| препятствие | где | решение |
|---|---|---|
| covergroup в классе вызывает методы своего класса (204 места) | покрытие ISA `uvme_rv32isa_covg.sv` | Verilator: вызов идёт через объект внешнего класса (IEEE 1800-2023 19.4) — `tools/verilator/ocv_tb_compat.patch`, тест `tools/verilator/test/t_cg_method.sv` |
| `%b` со строковым аргументом | логгер `uvma_clknrst_mon_trn_logger.sv` (неточность тестбенча) | Verilator: печатает строку как `%s` с предупреждением WIDTH (другие симуляторы печатают её биты; это строка журнала, не проверка) — тот же патч |
| `` `pragma protect ``, `super.new` не первым | агенты, `uvml_logs` | флаги `-Wno-BADSTDPRAGMA -Wno-SUPERNFIRST` |
| `bind модуль: экземпляр` | RTL-ассерты ядра (`CV32E40P_ASSERT_ON`) | Verilator не поддерживает — ассерты выключены (штатная настройка) |
| компонент ISS (`imperas_iss.flist`): DPI с неупакованными структурами, разбор дизассемблера ISS, память ISS в ассоциативном массиве через виртуальный интерфейс | Imperas (коммерческий) и `iss_wrap.sv` | `no_iss/gen_no_iss.py`: те же модули, порты и интерфейсы без поведения — как прогон без `+USE_ISS` |
| C++-имя `errno` (переменная в `uvml_mem`) — макрос glibc | `uvml_mem.sv` | Verilator: `errno`, `stdin/stdout/stderr` — в списке зарезервированных имён (переименовываются) |
| svlib: DPI на C, `io_printf` (PLI 1.0) | `svlib_dpi.c` | компилируется как C отдельно, `io_printf` = `printf`, `--vpi` |
| `always @(*)` с ожиданиями внутри крутится в момент 0 (Verilator теряет неявную чувствительность) | `step_compare.sv` (компонент ISS) | без ISS сравнивать нечего — модуль в `no_iss/` только с портами; ошибку Verilator стоит исправить отдельно |
| `randomize()` с пустым `rand`-указателем на объект: Verilator разыменовывал его (регистрация переменных, ограничения вложенного объекта, диапазоны `enum`) | базовый тест: `env_cntxt` создаётся в `build_phase`, после `randomize()` | Verilator: всё, что относится к объекту по пустому указателю, пропускается (IEEE 1800-2023 18.5.9); тест `tools/verilator/test/t_rand_null_member.sv` |
| ограничения, которые не берёт встроенный решатель OCV | конфигурации окружения | z3 (`pvo_scr1/ext/z3venv`, `pip install z3-solver`), `VERILATOR_SOLVER` |
| BSP требует newlib | `bsp/syscalls.c` | тулчейн xPack `riscv-none-elf-gcc` 15.2 (в `pvo_scr1/ext`), `prog.sh`; флаги теста — из `test.yaml` |

Итог: `vlt.sh lint` — 0 ошибок; `vlt.sh build` — 5 мин; `hello-world` — SIMULATION PASSED
(«HELLO WORLD!!!», exit 0, 110.6 мкс модельного времени, 12 с). Все изменения Verilator — в
`tools/verilator/ocv_tb_compat.patch` (ставит `tools/get_verilator.sh`).

## На плату: два варианта

**Вариант 1 — «как есть» (синхронно по тактам), `uvm/lockstep.py`.** Тестбенч целиком на ARM, без
подмен. Модуль ядра (`cv32e40p_wrapper`) заменён мостом с теми же именем и портами: в момент 0 и на
каждом спаде такта он отправляет в ПЛИС входы ядра и получает выходы того такта — ядро в ПЛИС делает
ровно один такт на запись (без записи заморожено). Сигналы внутри ядра, которые читает тестбенч
(иерархические ссылки, порты модулей, привязанных `bind`), приходят оттуда же каждый такт («пробы», 60
сигналов, 799 бит): мост держит теневую иерархию с теми же именами, так что ассерты отладки и прерываний
и покрытие работают на значениях ядра в ПЛИС. Такты внутри ядра (`core_i.clk` — после гейта сна)
строятся на ARM (`--clock`). Не из ПЛИС: трассировщик (`tracer_i.*`, модуль только для симуляции) и
регистровый файл — их читает только компонент ISS.

На ПК, ПЛИС смоделирована (`vlt.sh host`): совпадение с обычной симуляцией такт в такт —

| программа | конец теста | обычная симуляция | вариант 1 (host) |
|---|---:|---:|---:|
| hello-world | 110 601.300 нс | 12.1 с | 16.5 с |
| dhrystone | 1 381 902.300 нс | 129 с | 193 с |

На плате (VD100, ядро в ПЛИС на 50 МГц, тестбенч на A72; эталон пересобран с тем же решателем —
конфигурация выпадает одинаково):

| программа | конец теста | ПК, обычная симуляция | плата, вариант 1 |
|---|---:|---:|---:|
| hello-world | 80 211.300 нс (совпадает) | 8.9 с | 72 с |
| dhrystone | 1 007 580.300 нс (совпадает) | 104 с | 872 с |
| coremark | 18 436 119.300 нс (ПК) | 1 856 с | — (около 4 ч, не запускался) |

На плате ожидается медленнее ПК (профиль: ~470 мкс на такт уходит на пробуждение процессов тестбенча;
ARM слабее, плюс обмен на каждом такте) — вариант показывает, что чужой тестбенч идёт на плате без правок.

**Вариант 2 — ускоренный.** Всё, что работает на каждом такте, — в ПЛИС или в события по времени:
память OBI и задержки gnt/rvalid по настройкам теста, счётчик тактов периферии (из счётчика хаба),
таймер прерываний и управление отладкой (счётчики в ПЛИС, загружаемые записью программы), такт
тестбенча не тикает — время следует за ядром. На ARM — только редкие события (печать, статус, конец
теста, прерывания). Цена: SVA-ассерты (51) и потактовое покрытие отладки на ARM не вычисляются
(перечисляются в отчёте); результат программы, периферия, прерывания, конец теста — как есть.
Делается как ускоренные замены библиотечных агентов `uvma_obi_memory` (общих для тестбенчей OpenHW).

## Полный (сгенерированный) тест CV32E40P — общая обёртка `hw/cpu/` + `examples/cv32e40p/cv32e40p.bind`

Без UVM: программы генерирует модель на ARM во время прогона, каждая следующая — на непокрытые бины;
ядро в ПЛИС работает на своей частоте без тестбенча на тактах; проверка — каждой команды, по записям.
Обёртка общая для любых ядер (`hw/cpu/README.md`): ядро подключается файлом привязки, RTL ядра не меняется.

- Потоки CV32E40P (из сигналов, которые читает трассировщик ядра): *issue* — легальная команда, ушедшая
  из декодера; записи регистров через порт АЛУ и через порт LSU (результат при `wb_valid`, без
  промежуточной записи первой половины невыровненной загрузки); записи в память на шине.
- Модель: «fast»/«jit» с профилем `:cv32e40p` (`models/cpu/rv32_fast.c`), взятым из RTL ядра: строгое
  декодирование, таблица CSR ядра, исключения 2/3/11 на базу mtvec, mret.
- Генератор и покрытие `models/cpu/gen/cv32_gen.c`, `cv32_cov.c` (1693 бина): вычисления RV32IM, CSR
  (6 × 13 × 2), исключения (20 видов), все формы RVC (27), невыровненные обращения (12). Обработчик
  ловушек по 0x100 читает mcause и mepc в регистры (они сравниваются).
- Результаты (ПК): 6 программ, 364 тыс. команд, 100% покрытия, все потоки совпадают; эталон на ПК
  (`hw/cpu/run.sh … pc`, Verilator -O3, без хаба) — 0.95 с. Внесённые ошибки (`gen/faults.sh`): 5 из 5.
- Быстрое ядро в Verilator (~1 млн тактов/с) — не тот случай, где плата выигрывает много; выигрыш —
  на медленных тестбенчах (UVM) и больших ядрах.

Допущения: прерывания и отладка в генерацию не входят (`irq_i`, `debug_req_i` — нули); `wfi` не
генерируется; счётчики и регистры триггеров не читаются и не пишутся программами.
