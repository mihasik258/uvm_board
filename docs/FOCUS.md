# Фокус работы и план (с 22.10.2026)

Этот документ задаёт, на чём сосредоточены диплом и статья. Он уточняет `docs/PRODUCT_PLAN.md`:
- правила владельца из `docs/NEXT_PLAN.md` (раздел 0) и `docs/CLOUD_AGENT_PROMPT.md` остаются в силе;
- при расхождении с другими планами решает этот документ.

## 1. Цель

**Ускорить выполнение UVM-тестов функциональной верификации на гибридной системе «ПЛИС + ARM»** — для
процессорных ядер и больших IP-блоков. По словам научного руководителя, большие IP в тестировании занимают
даже больше времени, чем процессорные ядра.
- **«Без доработок» (решено с научным руководителем, 24.10.2026)** — это UVM-тест, написанный по нашим
  правилам и наследующий наши базовые классы. Такой тест идёт и в симуляции на ПК, и на плате без единой
  правки.
- **Основа — DUT и подключённые к нему интерфейсы; драйвер наследуется от нашего класса** (так предложил
  научный руководитель). Ограничения на тест задаются контрактом:
  - драйверы, мониторы и транзакции наследуются от универсальных классов `uvm/ocv_uvm_pkg.sv`. Они одни
    на все случаи и от теста к тесту не правятся;
  - с DUT тест общается только через SV-интерфейсы, подключённые к его выводам. Из них же генерируется
    обёртка DUT для ПЛИС;
  - правила — в шапке пакета: с DUT только через агенты; выводы только в `drive()`/`sample()`; без
    привязки к номеру такта; конец теста по транзакциям.
- **Метрики покрытия сохраняются:** покрытие RTL считается в ПЛИС, функциональное — на ARM (раздел 3а).
- **Существующие тестбенчи, написанные без нас** (core-v-verif), — через адаптер `uvm2board.py`, который
  подставляет те же базовые классы через фабрику. Это дополнительная демонстрация, не главный результат.

Цель совпадает с защищённой темой ВКР (слайды 14.10.2026): объект — процесс функциональной верификации
с помощью UVM-тестов, предмет — методы их исполнения на гибридной системе. Название не меняется.

**Тезис статьи:**

> UVM-тест процессорного ядра или большого IP-блока, написанный по контракту (наследование от универсальных
> базовых классов), без правок выполняется и в симуляции, и на недорогой плате «ПЛИС + ARM»: длинная
> регрессия, которая на ПК идёт часами, на плате занимает минуты; покрытие RTL считается в ПЛИС,
> функциональное — на ARM. Выигрыш определяется числом тактов DUT на транзакцию теста.

## 2. Мерило: выигрыш в часах, а не в секундах

- **Считаются только длинные тесты.** На ПК (чистый UVM в Verilator) они идут часы и дольше, на плате —
  минуты.
- **Главные метрики:**
  - время до первой ошибки на длинной регрессии;
  - время одного длинного теста.
- Короткие тесты (hello, dhrystone, coremark — секунды и минуты на ПК) — только проверка, что путь работает.
  В главную таблицу они не идут.
- **ПК для сравнения** — ноутбук владельца (Core Ultra 7 155H, одно P-ядро), как во всех прежних замерах.
  Облачные машины для эталонных цифр не годятся.
- Прогон на ПК длиннее 10 ч можно оценить по измеренной скорости. Такая цифра помечается как оценка, и
  рядом приводится скорость, на которой она основана.

Ориентиры скорости:
- чистый UVM core-v-verif на ПК — около 1,2–1,5 тыс. команд/с (coremark, 2,79 млн команд, за 1856–2257 с);
- 1 ч на ПК — около 5 млн команд, сутки — около 120 млн.

## 2а. Граница метода: такты DUT на транзакцию

Граница проходит не между IP и процессорами, а по числу тактов DUT на одну транзакцию теста:
- **на ПК** время растёт с числом тактов и с размером схемы: Verilator на большой схеме медленнее за такт;
- **на плате** такт DUT почти бесплатен (ПЛИС — десятки МГц), а время определяет число транзакций, которые
  обрабатывает ARM: `randomize()`, передача, scoreboard.

| DUT | тактов на транзакцию | выигрыш платы |
|---|---:|---:|
| mac16 (малый IP, операция за такт) | 1 | ×0,5 — худший случай |
| SHA-256 (блок 512 бит) | ~65 | ×5 |
| SCR1 с моделью (тест почти не вмешивается) | — | ×76 |
| большой IP (план 4.9) | тысячи | ожидается больше всего |

Итог: малые IP с короткими транзакциями — ПК; большие IP и процессоры — плата. Кривая «выигрыш от тактов
на транзакцию» — план 4.10, главный график статьи о том, когда плата выгодна.

## 3. Что входит в работу и как

| часть | роль для цели | в статье |
|---|---|---|
| контракт: базовые классы и правила (`uvm/ocv_uvm_pkg.sv`) | основа переноса без доработок | главный вклад |
| хаб и обёртка ядра (`hw/rtl`, `hw/cpu`, `.bind`) | ядро подключается без ручной правки RTL | архитектура |
| эталон на A72 (JIT), сверка подписями окон | без них UVM-тест на ARM не ускоряется | средство; сравнение с DiffTest-H |
| адаптер для существующих тестбенчей (`uvm2board.py`, `tbparse.py`, `uvm_fast`) | чужой тест без нашего контракта | дополнительно |
| контрольная точка → VCD на ПК (`tools/ckpt_replay.sh`) | ошибку с платы можно отладить | кратко |
| функциональное покрытие по отобранным записям (`docs/COVERAGE.md`, 2.3) | исходные covergroup на ARM | вероятная новизна |
| покрытие RTL в ПЛИС (план 4.8) | метрика кода без потери скорости | да, если успеем |
| тест 2 (CVA6 без UVM, `minstreth` ×95) | довод «работает и на большом ядре» | вспомогательно; не выдавать за UVM-результат |
| большой IP-блок с тестом по контракту (план 4.9) | второй показательный пример, рядом с CVA6 | да |
| малые IP (mac16 ×0,5, SHA-256 ×5) | точки кривой «выигрыш от тактов на транзакцию» | да, на графике (4.10) |

## 3а. Покрытие

| вид | где | статус |
|---|---|---|
| покрытие кода RTL (ветви, переходы автоматов; toggle — позже) | ПЛИС: счётчики, которые вставляет инструмент; ARM читает их в конце прогона | нет, план 4.8 |
| функциональное по транзакциям (covergroup теста, isacov) | ARM, исходные covergroup; при нехватке скорости — с фильтром записей | есть, точность проверена на ПК; на плате — 4.4 |
| функциональное по внутренним сигналам каждый такт | не делаем; редко меняющиеся сигналы — поток `watch` | в ограничения |

«RTL без изменений» уточняется: RTL автора не правится руками. Счётчики покрытия инструмент вставляет
автоматически, и только в сборку для ПЛИС.

## 4. План

### 4.1. UVM-тест процессорного ядра по контракту и длинный сценарий для него — без платы

- **Тест.** UVM-тестбенч ядра по нашим правилам:
  - агенты и транзакции наследуют `ocv_uvm_pkg`;
  - scoreboard сверяет с эталонной моделью через DPI (`ocv_checker`);
  - функциональное покрытие — covergroup isacov из core-v-verif на транзакциях монитора.

  Образец — `examples/scr1/uvm`, но без ручного `scr1.json` (см. 4.7).
- **Ядро — CVA6, рекомендация.** Внесённая ошибка `minstreth` (перенос после 2³² команд) и программа
  nettle-aes ×1100 уже есть. Образ ПЛИС на 50 МГц собран, без UVM на ПК известно 8,3 ч. Запасной вариант —
  CV32E40P.
- **Готово, когда:**
  - тест без правок идёт в симуляции на ПК и в режиме платы на ПК (ПЛИС смоделирована);
  - на исправном ядре — PASS;
  - на ядре с ошибкой ошибка найдена.

### 4.2. Путь UVM-теста выдерживает миллиарды команд — без платы

- Проверить потоковое сравнение (`stream_compare`) на пути UVM-теста. В 1б без него прогонщик
  падал по нехватке памяти через 15 с.
- 64-битный счётчик записей хаба `taken` — пересборка образов (Vivado, у владельца).
- **Готово, когда** длинный прогон в режиме платы на ПК идёт с постоянной памятью, а номера записей больше
  2³² считаются верно.

### 4.3. Эталон на ПК — у владельца

- Тот же длинный UVM-тест (4.1) в симуляции, Verilator на ноутбуке.
- Один настоящий прогон 8–10 ч либо замер скорости за несколько часов и оценка.
- **Готово, когда** есть время до ошибки на ПК (измеренное или оценка с её основанием).

### 4.4. День с платой

1. Короткая проверка: `docs/BOARD_DAY.md` — hello, coremark, SCR1, CVA6; попутно тест 1 core-v-verif через
   адаптер.
2. **Длинный прогон с внесённой ошибкой:** время до ошибки, пропускная способность, 0 ложных
   расхождений на исправном ядре.
3. Попутно — цена фильтра покрытия на A72 (`OCV_BENCH_ARCH=aarch64`). По ней решается этап 2.5:
   - если цена приемлема — фильтр в jit;
   - если нет — на плате только отбор записей, covergroup на ПК.
- **Готово, когда** в главной таблице есть строка «UVM-тест верификатора, время до ошибки: ПК — часы, плата —
  минуты».

### 4.5. Незнакомое ядро без ручной работы (усиливает «без доработок»)

- Ibex или PicoRV32 — скачивание в `ext/` с разрешения владельца.
- Записать каждый ручной шаг. Цель — ноль шагов, кроме выбора файлов.
- **Готово, когда** новое ядро проходит регрессию в режиме платы на ПК без правок нашего кода под него.

### 4.6. Текст

- Документ для научного руководителя: лид и выводы под цель из раздела 1, FERIVer в литературе.
- Слайды 3 и 5: источник цифр 7,8 МГц / 4 кГц (это DiffTest-H, XiangShan); «миллиарды», а не «миллионы»
  тактов.
- **Главная таблица статьи** — в часах (раздел 2). Сравнение с ENCORE, DiffTest-H, Lyra, ZynqParrot, FERIVer —
  по осям «готовый UVM-тест» и «цена оборудования», а не по чистой скорости. По скорости они быстрее.

### 4.7. Упаковка транзакции по умолчанию — без платы

- Сейчас `to_rec()`/`from_rec()` в `ocv_item` объявлены как `pure virtual`, и их генерирует скрипт по
  описанию (`scr1.json`). Нужна упаковка по умолчанию в базовом классе по полям транзакции:
  - стандартный `pack`/`unpack` UVM по полям `uvm_field_*`, если `uvm_packer` работает в нашем Verilator
    на A72 и не слишком медленный;
  - иначе — генерация по классу транзакции.
- Обёртка ядра для ПЛИС — из того же SV-интерфейса.
- **Готово, когда** тест из 4.1 собирается без ручного описания схемы: только интерфейс, классы теста и
  RTL.

### 4.8. Покрытие RTL в ПЛИС, минимальный вариант — после 4.4

- **Одно ядро** — SCR1 или CV32E40P, без CVA6.
- **Метрики:** ветви и переходы автоматов.
- **Инструмент** вставляет синтезируемые счётчики в сборку для ПЛИС: Yosys; для SystemVerilog — sv2v
  или Synlig. ARM читает счётчики в конце прогона.
- **Опора:** Under Cover, ZynqParrot, DifuzzRTL.
- **Готово, когда:**
  - на одном тесте покрытие из ПЛИС совпадает с покрытием Verilator на ПК;
  - расход ресурсов ПЛИС измерен.

### 4.9. Большой IP-блок — тест по контракту и длинный сценарий

- **Выбор кандидата.** Требования:
  - открытый RTL и подходящая лицензия;
  - помещается в ПЛИС VD100 (VE2302 небольшая — проверить по ресурсам);
  - есть эталон на C для scoreboard: для криптографии и сжатия просто, для кодеков сложнее;
  - на ПК длинный тест идёт часами;
  - тысячи тактов DUT на транзакцию.

  Кандидаты проверить: IP-блоки OpenTitan (AES, KMAC/SHA-3, OTBN — у них есть свои UVM-окружения, это
  ориентир для времени на ПК), открытые FFT и JPEG-кодеры. Скачивание в `ext/` — с разрешения владельца.
- **Тест** — по контракту, как в 4.1: агенты от `ocv_uvm_pkg`, упаковка по умолчанию (4.7), эталон на C
  через DPI, covergroup на транзакциях.
- **Внесённая ошибка**, которая проявляется на длинном сценарии.
- **Готово, когда:**
  - тест без правок идёт в симуляции и в режиме платы на ПК;
  - на плате есть время одного длинного теста и время до ошибки против ПК — в часах.

### 4.10. Кривая «выигрыш от тактов на транзакцию»

- **Точки:** mac16 (1 такт), SHA-256 (~65), большой IP (4.9), CVA6 (4.1). Все тесты — по контракту.
- Для одного IP по возможности меняем длину транзакции (размер блока или пакета), чтобы увидеть ход
  кривой на одном DUT.
- **Готово, когда** есть график и простая модель:
  - время на ПК ≈ такты × цена такта (зависит от размера схемы);
  - время на плате ≈ max(транзакции × цена на ARM, такты / частота ПЛИС).

**Порядок:**
1. 4.1 и 4.7 — вместе (тесту нужна упаковка по умолчанию); 4.2 параллельно. Всё без платы.
2. 4.3 — у владельца, можно начинать сразу.
3. 4.9: выбор кандидата — сразу; тест — после 4.1.
4. 4.4 — день с платой; на нём же, если готов, большой IP.
5. 4.10 — по мере появления точек.
6. 4.8 — после 4.4.
7. 4.5 и 4.6 — в паузах.

## 5. Чего не делаем

- Не ускоряем короткие тесты и тест A: выигрыш в секундах статье не нужен.
- Не берём малые IP с короткими транзакциями как показательный пример: там ПК быстрее (mac16 ×0,5). Они
  нужны только как точки кривой (4.10).
- Не соревнуемся с ENCORE, DiffTest-H и Lyra в мегагерцах.
- Не делаем функциональное покрытие по внутренним сигналам каждый такт (синтезируемые covergroup) — это
  в ограничения.
- **Новое направление только с согласия владельца:** второе ядро A72, копии DUT, частота ПЛИС, перенос
  тестбенча CVA6 целиком.

## 6. Риски

- **Чужой тестбенч может упереться в скорость ARM.** Это пробуждения процессов UVM; вариант E1 на плате медленнее ПК.
  Тест 1 (`uvm_fast`) обходит это: до тестбенча доходят только обращения к периферии. Но на длинных
  программах это ещё не проверено.
- **Фильтр покрытия не насыщается.** Записей остаётся примерно столько, сколько корень из длины теста. Для
  статьи достаточно точности, скорость фильтра — в ограничения. Улучшение: брать группу команды у
  тестбенча (`get_instr_group`).
- **Плата одна, ядра малые (RV32).** Это пишется в ограничения прямо.
- **Большой IP может не поместиться в VE2302.** Кандидата выбираем по ресурсам заранее, до того как писать
  тест.
- **Эталон на C для IP** нужно взять готовый (OpenSSL, эталонные реализации стандартов), а не писать самим.
