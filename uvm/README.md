# UVM-слой OCV: тест из симуляции — на плату без переписывания

Верификатор пишет обычное UVM-окружение и тесты на SystemVerilog — **свои** интерфейс, транзакции,
драйверы, мониторы, агенты, scoreboard и вершину с ядром, как для любого симулятора. Ничего для
платформы он не пишет: ни описания ядра, ни наследования от наших классов.

- **симуляция** — как обычно (Verilator: `run.sh pc`, или любой другой симулятор);
- **плата** — скрипт `uvm2board.py` читает тестбенч (`tbparse.py`: каналы ядра — из интерфейса,
  драйверов, мониторов и вершины) и пишет оверлей; Verilator компилирует окружение в программу для
  ARM гибридной СнК, ядро стоит в ПЛИС той же платы. Компьютер для прогона не нужен.

## Тестбенч как есть → плата (без описания ядра)

Примеры: `examples/scr1/uvm_v`, `examples/mac16/uvm_v`, `examples/sha256/uvm_v`
(`run.sh pc | host | aarch64 | vd100 | sd | wave`).

**Что платформа берёт из тестбенча** (`tbparse.py`; всё, что не подходит, — ошибка с причиной):

| что нужно | откуда |
|---|---|
| модуль ядра, такт, сброс | вершина: экземпляр ядра с именованными подключениями; `always #N clk = ~clk;`; сброс — сигнал, который вершина ставит в одно значение, затем в другое (полярность — по первому) |
| выводы и ширины | объявления сигналов SV-интерфейса (`logic [signed] [N:M] x;`) |
| входной канал | `uvm_driver`: в цикле `get_next_item(t)`, `vif.x <= t.f`, `vif.valid <= 1`, ожидание `vif.ready`, `vif.valid <= 0` |
| выходной канал | `uvm_monitor`: `@(posedge vif.clk); if (vif.valid [&& vif.ready]) begin t.f = vif.x; ap.write(t); end` (условие сброса допускается); ready — тот из двух сигналов, который присваивает сам тестбенч |
| монитор на входных выводах | монитор, чьи сигналы совпадают с сигналами драйвера: на плате он получает записи, которые драйвер отправил в ПЛИС |
| что сравнивать | scoreboard (ниже), маска — регистром ПЛИС при запуске |
| глубины буферов, «без потерь», свёртка | решает платформа: все выходы без потерь, свёртка доступна везде |

**Что делает оверлей для платы:** подменяет через фабрику драйверы и мониторы верификатора на
транспорт (упаковка полей в запись хаба генерируется), scoreboard — на движок A, последовательности
— на блоки; вершина для платы — его вершина без ядра и без тактового генератора. `+OCV_ASIS`
отключает только ускорения (движок A, блоки); транспорт нужен всегда — ядро в ПЛИС.

Проверено (ПК, образ ПЛИС смоделирован): SCR1 — r1/r2 PASS, свёртка (89 записей на 361 653
команды), ошибка ядра найдена на той же команде, что исходным тестом (#127); mac16 — 2000/2000, 0
ошибок (scoreboard на SV с моделью от монитора входа — идёт как есть). Описание, выведенное из
тестбенча SCR1, совпадает с прежним ручным `scr1.json` (выводы, ширины, рукопожатия, такт, сброс).
Тесты: `test/t_tbparse.py` (8 вариантов), `test/t_uvm2board.py` (11).

Сигнал шире 64 бит (поле хаба — до 64) делится на части по 64 бита одного вывода (`slice` в
описании); запись слоя UVM — до 1024 бит. Пример: `examples/sha256` (блок 512 бит, дайджест 256 бит,
эталон FIPS 180-4 на SV в scoreboard): 10 000 блоков на ПК — 3.37 с, форма для платы на ПК
(ПЛИС смоделирована) — 0.94 с.

**На плате** (VD100; тестбенчи без описания ядра; эталон — те же тестбенчи в Verilator на ПК;
0 ошибок везде):

| тест | проверка | ПК | плата, как есть | плата, с ускорениями |
|---|---|---:|---:|---:|
| SCR1 r1 / r2 / r3 (36 тыс. / 362 тыс. / 3.7 млн команд) | модель через DPI (движок A) | 1.08 / 8.85 / 84.3 с | 3.81 / 13.9 / 117 с | 0.18 / 0.40 / 2.65 с (×6–32) |
| SHA-256, 10 тыс. / 100 тыс. блоков | SV в scoreboard | 3.37 / 33.6 с | 3.30 / 31.5 с | 0.74 / 6.57 с (×4.5–5.1) |
| mac16, 20 тыс. / 200 тыс. | SV в scoreboard | 0.85 / 7.69 с | 8.04 / 77.8 с | 1.67 / 16.05 с (×0.5) |
| SCR1 dhrystone (165 тыс. команд, читает счётчики тактов) | модель + значения счётчиков от ядра | 2.38 с | 10.2 с | 0.247 с (×9.6) |

Тест без модели выигрывает, когда за транзакцией стоят десятки тактов ядра; у mac16 (такт на
транзакцию) время уходит на `randomize()` на ARM. Verilator 5.052 не учитывает веса `dist`
(выбирает равномерно) — и на ПК, и на плате.

### Одной командой на SD-карту

```bash
examples/scr1/uvm_v/run.sh sd     # = RTL=... uvm/make_sd.sh scr1 tb_top <файлы тестбенча>
```

`make_sd.sh`: разбор тестбенча → образ ПЛИС (Vivado, около часа; пропускается, если не изменились
каналы, RTL, его define, хаб OCV, платформа, частота) → тестбенч для A72 → папка `sdcard/`:
`BOOT.BIN` (и копия `BOOT_<имя>.BIN`), `image.ub`, `boot.scr`, `ocv/<имя>/` — программа, данные
тестов (`PAYLOAD`), `run.sh`. Скопировать всё на FAT-раздел карты; на плате:
`sh /run/media/FAT-mmcblk1p1/ocv/scr1/run.sh +UVM_TESTNAME=prog_test +PROG=r2.hex`.
Нужны `VIVADO_SETTINGS`, `REF_BOOTBIN`, `LINUX_DIR` (как для `platforms/vd100/build.sh`).

### Ошибка на плате → временная диаграмма на ПК

При первой ошибке плата печатает строку с аргументами теста и номером записи:

```
OCV: waveform on a PC (...): +UVM_TESTNAME=prog_test +PROG=r2.hex +OCV_WAVE=retire:127
```

Номер — у движка A точный (при свёртке — после повтора с `+OCV_SQUASH=1`); у scoreboard на SV —
сколько записей канал отдал в UVM к моменту ошибки (scoreboard проверяет запись, когда её пишет
монитор). На ПК тот же тест в обычной симуляции:

```bash
examples/scr1/uvm_v/run.sh wave +PROG=<hex> +OCV_WAVE=retire:127   # (путь к файлам — ПК)
```

`build_board.sh wave` оборачивает вершину верификатора (не меняя её) модулем от `tbwave.py`: он
считает передачи каждого канала на выводах ядра (valid, и ready, если есть — как их видит монитор)
и пишет VCD (`ocv_wave.vcd`) от `+OCV_WAVE_BEFORE` записей до (20) до `+OCV_WAVE_AFTER` тактов после
(200), затем завершает симуляцию. Сборка с трассировкой — отдельная (`pc` для замеров не меняется).
Проверено на ядре с внесённой ошибкой (r2, sra как логический сдвиг): плата (форма host, свёртка и
как есть) называет `retire:127`; на ПК scoreboard сообщает об ошибке в 168 505 000 пс — в тот же
момент обёртка отмечает запись 127; файл — 0.7 МБ.

Сгенерированные агенты по json (`ocv_gen.py --uvm`, примеры `examples/*/uvm`) остаются как
необязательное удобство.

## Из чего состоит

| Файл | Что |
|---|---|
| `ocv_uvm_pkg.sv` | базовые классы: транзакция `ocv_item`, драйвер `ocv_source_driver`, монитор `ocv_monitor`, агенты; в сборке для платы — DPI к хабу |
| `ocv_uvm_dpi.c` | связь UVM ↔ библиотека OCV: потоковые источники, выходы без потерь, один опрос хаба на все каналы |
| `ocv_uvm_bus_mmap.c` | шина на плате (`/dev/mem`) |
| `ocv_uvm_bus_vlt.cpp` | шина на компьютере: образ ПЛИС (хаб + ядро) как модель Verilator — тот же путь, что на плате |
| `vlt/ocv_fast_random.cpp` | встроенный решатель ограничений для `randomize()` (ниже) |
| `run_uvm.sh` | запуск в xsim: `sim` (выводы) или `pcboard` (путь платы, ПЛИС смоделирована) |
| `build_board.sh` | сборка Verilator: `aarch64` (программа для VD100), `host` (то же на компьютере с моделью ПЛИС), `pc` (без платы: окружение и RTL ядра в одной модели — базовый вариант для сравнения) |
| `tbparse.py` | каналы ядра из тестбенча верификатора (интерфейс, драйверы, мониторы, вершина) — вместо описания |
| `uvm2board.py` | перевод теста для платы: транспорт вместо драйверов/мониторов, scoreboard → движок A, последовательности → блоки (ниже) |
| `test/` | тест решателя (`run_tests.sh`, входит в `test_all.sh`, шаг 11) |

Генератор строит по описанию ядра (`ocv_gen.py --uvm`) классы транзакций каждого канала (поля, правила
сравнения из описания → `do_compare`/`mismatch()`), агенты, драйверы и мониторы выводов для симуляции,
обвязку `<имя>_ocv_uvm_harness` (часы, сброс, ядро; на плате — пустая). Хаб строится для транзакций:
источники — потоковые, мониторы — без потерь (ядро ждёт, пока окружение не заберёт данные).

Агенты верификатора могут наследоваться от базовых классов: в симуляции реализуются `drive()` и
`sample()` (работа с выводами), на плате их заменяет обмен с ПЛИС.

## Правила для тестов, которые должны идти и на плате

1. С ядром — только через агенты OCV (или наследников базовых классов): без иерархических ссылок
   внутрь ядра и прямого доступа к выводам.
2. Работа с выводами — только в `drive()` / `sample()`; последовательности, scoreboard, покрытие,
   модели — на уровне транзакций.
3. Нельзя полагаться на такт, в котором случилась транзакция: ядро на плате работает на своей
   частоте, окружение — в темпе процессора (ядро его ждёт, данные не теряются).
4. Тест завершается по транзакциям (получено ожидаемое число), а не по задержке.
5. `dist` с весами — в ограничениях класса: во встроенных `randomize() with {...}` Verilator 5.052
   веса отбрасывает (значения равновероятны).

Время на плате: окружение не использует произвольных задержек. Один процесс опрашивает хаб и
продвигает время окружения ровно на столько тактов, сколько ядро прошло в ПЛИС, — `$time` означает
время ядра, как в симуляции.

## Встроенный решатель ограничений

Verilator решает каждый `randomize()` с ограничениями внешним SMT-решателем (z3) через канал:
несколько запросов на вызов, ~17–44 мс. Это главное узкое место UVM на процессоре. Решатель OCV
(`vlt/ocv_fast_random.cpp`) работает внутри программы:

1. ограничения (SMT-текст, как их строит Verilator) компилируются в дерево выражений, с кэшем;
2. ограничение на одну переменную из сравнений с константами, `and/or/not`, `inside`, `dist`,
   расширений и сложения/вычитания известных величин сводится к множеству допустимых значений
   (объединение интервалов);
3. переменные, связанные ограничениями, разбиваются на независимые группы; в группе — независимый
   выбор с отбраковкой (строго равномерно по решениям), при неудаче — последовательный выбор с
   подстановкой уже выбранных (близко к равномерному, как сэмплер самого Verilator);
4. всё остальное (массивы, `randc`, `unique`, мягкие ограничения, `solve before`, незнакомые
   операции) — как раньше, в z3.

Подключение — одна точка в runtime Verilator (`tools/verilator/ocv_fast_random.patch`, ставит
`tools/get_verilator.sh`). `OCV_FAST_RANDOM=0` — выключить (для сравнения),
`OCV_FAST_RANDOM_DEBUG=1` — почему вызов ушёл в z3. Счётчики — в итоговой строке `[OCV]`.

## Запуск

```bash
tools/get_verilator.sh                       # Verilator 5.052 + UVM + решатель OCV (один раз)
E=examples/mac16
RTL=$E/mac16.sv uvm/run_uvm.sh sim     $E/mac16.json tb_top $E/uvm/mac16_tb_pkg.sv $E/uvm/tb_top.sv -- +N=1000
RTL=$E/mac16.sv uvm/run_uvm.sh pcboard $E/mac16.json tb_top $E/uvm/mac16_tb_pkg.sv $E/uvm/tb_top.sv -- +N=1000
uvm/build_board.sh aarch64 $E/mac16.json tb_top $E/uvm/mac16_tb_pkg.sv $E/uvm/tb_top.sv
# образ ПЛИС: OCV_GEN_FLAGS=--uvm platforms/vd100/build.sh $E/mac16.json $E/mac16_model.c $E/mac16.sv
# на плате:  ./tb_top +OCV_BASE=0x80000000 +N=100000
```

## Перевод теста для платы: `uvm2board.py`

Тест верификатора не меняется. Скрипт разбирает окружение и пишет оверлей `board_overlay.sv`
(пакет `<ядро>_board_pkg` и модуль `<top>_board` — вершина сборки для платы):

- **scoreboard** канала со `squash` в описании, который сравнивает транзакции с моделью через DPI, →
  наследник `<класс>_board`. Проверку делает движок A на ARM: ПЛИС сворачивает окна по N записей
  в подписи CRC, модель (`board_ref.c` — обёртка той же DPI-модели) считает те же подписи. При
  расхождении программа перезапускается с окном 1 и находит первую неверную запись (replay), в
  сообщении — её номер (`record #N`). Поля scoreboard (счётчики, признак конца) заполняются из
  движка, поэтому тест, который их ждёт, работает без изменений;
- **последовательности**, которые шлют записи в цикле `start_item`/`finish_item`, → наследники,
  которые шлют те же записи одним блоком (объект-носитель создаётся один раз, до цикла).

**Что сравнивается — берётся из scoreboard, а не из описания ядра.** Скрипт разбирает `write()`
по операторам и переводит его, только если понимает каждый: объявления; один вызов DPI-модели (без
условия, только выходные аргументы); заполнение ожидаемого объекта её выходами; сравнение полей
(`t.f != m.f`, обе стороны с одинаковой маской `(t.f & C) != (m.f & C)`, `||` таких сравнений,
строка с именем поля, `!t.compare(m)` с `do_compare` вида `a == o.a && ...` или макросами полей без
`UVM_NOCOMPARE`); счётчики; в ветке расхождения — счётчик ошибок и `uvm_error`/`$display`; конец
теста `if (t.f == <значение>) <флаг> = 1;`. Из сравнений получается таблица «поле → сравниваемые
биты» (`board_ref.c`, `OCV_UVM_CHECKER_CMP`); по ней ARM сравнивает записи, и её же он записывает
в ПЛИС как маску подписей (регистры `SQMASK_SEL`/`SQMASK`, флаг `KIND_SQMASK`; со старым образом
без них свёртка включается, только если маски совпадают, иначе — проверка по одной записи).

**Стили сравнения:** явные `!=`/`!==` по полям (в т.ч. с одинаковой маской, через `||`), строка с
именем поля, `if (!t.compare(m))` с `do_compare` вида `a == o.a && ...` или макросами `uvm_field_*`
(без `UVM_NOCOMPARE`), `assert (t.a == m.a && ...) else ...`, `if (все равны) ; else ...`. Счётчик
ошибок должен увеличиваться в одном месте (иначе число ошибок на плате было бы другим); `assert` без
`else` — отказ (провал не считается scoreboard). Тест — `test/t_uvm2board_own.py`.

**Сравнение с допуском.** `(t.f > m.f ? t.f - m.f : m.f - t.f) > K` (любой порядок, `>` или `>=`)
переводится в правило «модуль разности не больше K» (`board_ref.c`, `kind 1`); знаковость поля — из
интерфейса. Подпись CRC такое сравнение не выражает, поэтому канал проверяется движком A по одной
записи в C, без свёртки (записи читаются из ПЛИС пачками, UVM на запись не работает — на плате это
режим «окно 1»: SCR1 r3 7.1 с против 117 с «как есть»). Форма `t.f - m.f > K || m.f - t.f > K` не
принимается: на беззнаковых полях она переполняется и значит не то, что задумано.

**Значения от ядра (таймеры, устройства).** Если scoreboard перед шагом модели передаёт ей значение
из транзакции ядра (`if (t.csr_rd && t.csr_addr inside {...}) ref_timer(t.rd_wdata);` — вызов DPI только
с входами-полями транзакции, под условием на неё), это переводится так же, как в DiffTest: из условия
выводятся образцы (маска/значение по полям, список `inside` сжимается в кубы; не больше 4, при
нехватке — с запасом), ПЛИС закрывает окно свёртки на каждой записи, совпавшей с образцом
(`EP_REG_BRK_SEL/BRK_DATA`, `KIND_SQBRK`), и эта запись — последняя запись окна целиком; движок
отдаёт её модели как `dut`, `board_ref.c` проверяет то же условие и вызывает ту же функцию. Без
прерывателя в образе — проверка по одной записи. Пример: dhrystone (чтения счётчиков) — 164 891
команда, 41 запись из ПЛИС, 0 ошибок (раньше не проходил и в симуляции: модель не знала значения
таймера). Для этого в отвод RVFI-lite SCR1 добавлены признак и номер прочитанного CSR (биты 102..114).

**Не по порядку** (сопоставление по ID, ассоциативные массивы ожидаемых) движок A не переводит: модель
там вызывается не на каждую выходную запись по порядку. Такой scoreboard идёт путём UVM с блоками и
одним объектом на монитор (как mac16 и SHA-256).

**Покрытие при свёртке.** Если к монитору кроме scoreboard подключены подписчики (сборщики
покрытия), которые читают только сравниваемые поля транзакции, они получают проверенные записи: со
свёрткой — записи модели после совпадения подписи окна (в сравниваемых битах они равны записям
ядра), без свёртки — записи ядра. Подписчик, читающий несравниваемое поле или берущий транзакцию
целиком, — причина отказа. Проверено: SCR1 r2 со сборщиком покрытия — счётчики на форме для платы
(окно 4096, окно 1, как есть) совпадают с обычной симуляцией бит в бит, свёртка остаётся (89 записей).

**Отказ вместо молчания.** Всё остальное — циклы, условный вызов модели, сравнение с допуском,
разных полей, `mismatch()` сгенерированного объекта, запись в журнал на каждую транзакцию, любой
посторонний оператор, второй подписчик монитора (покрытие — на плате он не получил бы транзакций)
— причина оставить scoreboard как есть: скрипт пишет, что именно и почему, и эта часть идёт на плате
по одной транзакции через UVM (верно, но без ускорения). Тест скрипта — `test/t_uvm2board.py`
(11 вариантов scoreboard: переведён с точной таблицей сравнения или отклонён с причиной).
