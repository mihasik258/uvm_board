# OCV — архитектура и контракты

OCV (On-Chip Verification) — аппаратно-программная платформа для верификации IP-ядер на
кристалле гибридной СнК (ПЛИС + процессорная система). Тестируемое ядро (DUT) работает в
ПЛИС; платформа подаёт на него стимулы, захватывает его транзакции и сверяет каждую с
эталонной моделью на процессорной системе.

Чтобы подключить новое ядро, нужны **описание** (JSON, [DESCRIPTOR.md](DESCRIPTOR.md)) и
**модель** (C, [ocv_model.h](../sw/include/ocv_model.h)). Всё остальное генерируется или общее.

## 1. Слои

```
   описание DUT (JSON) ──ocv_gen.py──►  <dut>_ocv.sv  +  <dut>_ocv_meta.h
                                             │                  │
 ┌───────────────── ПЛИС ────────────────────▼──┐   ┌──── PS (Linux) ▼ ───────────────────┐
 │  <dut>_ocv  (сгенерированная обёртка)         │   │  ocv_runner  (общий прогон)          │
 │   ┌────────┐  ┌─────────┐  ┌────────┐         │   │   ├ ocv.c    доступ, поля, сверка     │
 │   │ source │─►│   DUT   │─►│  sink  │ ...     │   │   └ модель DUT (плагин, C)          │
 │   └───▲────┘  └────┬────┘  └───▲────┘         │   │                                     │
 │       │  monitor ◄─┘ (наблюдение)│             │   │  шина: mmap(/dev/mem) на плате,     │
 │   ┌───┴──────────────────────────┴───┐         │   │        AXI-транзакции в косимуляции  │
 │   │ ocv_hub: одно окно AXI4-Lite     │◄────────┼───┤                                     │
 │   └──────────────────────────────────┘         │   └─────────────────────────────────────┘
 └────────────────────────────────────────────────┘
          ▲ платформенный слой (platforms/<плата>/): подключение окна хаба к PS, такты, сброс
```

| Слой | Где | Знает о DUT | Знает о плате |
|---|---|---|---|
| Ядро платформы | `hw/rtl`, `sw/lib`, `gen`, `sim` | нет | нет |
| Адаптер DUT | описание + модель (`examples/<dut>/`) | да | нет |
| Платформенный слой | `platforms/<плата>/` ([VD100](../platforms/vd100/README.md)) | нет | да |

Ключевое свойство: у сгенерированной обёртки **любого** DUT наружу один и тот же интерфейс —
одно окно AXI4-Lite. Поэтому платформенный слой пишется один раз на плату и не меняется при
смене DUT.

## 2. Аппаратное ядро (`hw/rtl`)

| Модуль | Назначение |
|---|---|
| `ocv_hub` | единственный AXI4-Lite слейв окружения; слот 0 — каталог и управление DUT, слоты 1..N — конечные точки |
| `ocv_axil_slave` | AXI4-Lite → простая регистровая шина с фиксированной задержкой чтения |
| `ocv_source` | стимулы: PS пишет записи в буфер, source выдаёт их на valid/ready-вход DUT до одной записи за такт |
| `ocv_sink` | захват: пассивный монитор или приёмник потока с backpressure (без потерь) |
| `ocv_capture` | логика захвата внутри sink (заполнение, переполнение, счёт потерь, stall) |
| `ocv_throttle` | псевдослучайные паузы (LFSR) для нагрузки логики управления потоком DUT |
| `ocv_clock_gate` | вентиль такта DUT: замораживает DUT, пока полон буфер монитора `lossless` |
| `ocv_ram` | буфер записей, вывод из RTL, побайтовая запись |

Правила, которые соблюдает ядро:
- поток к DUT соблюдает AXI-Stream: выставленный valid держится с неизменными данными до
  рукопожатия (проверяется в тестбенче на каждом такте);
- всё, что идёт из платформы в DUT, выходит прямо с регистров — тайминг DUT не зависит от
  логики платформы;
- один тактовый домен: DUT и окно AXI4-Lite тактируются одним `clk`; если у DUT есть монитор
  `lossless`, его такт идёт через `ocv_clock_gate`, и конечные точки учитывают передачу только
  в тех тактах, где DUT тикает (`dut_ce`) — замороженный DUT ничего не отдаёт и не теряет;
- сброс DUT (`DUT_CTRL`) заодно очищает захват и перематывает стимулы — каждый прогон с нуля.

## 3. Контракты

### 3.1. Адаптер DUT ↔ ядро (RTL)
Его генерирует `ocv_gen.py` по описанию; вручную писать не нужно. Виды каналов, порты и
упаковка полей — в [DESCRIPTOR.md](DESCRIPTOR.md).

### 3.2. Ядро ↔ программа на PS (регистры)
Аппаратная половина — `hw/rtl/ocv_pkg.sv`, программная — `sw/include/ocv_regs.h`.
`hw/scripts/check_regs.py` требует, чтобы **каждая** константа пакета имела пару в заголовке
с тем же значением.

Хаб (слот 0):

| Смещение | Регистр | Доступ | Содержимое |
|---|---|---|---|
| `0x00` | ID | RO | `0x4F434801` |
| `0x04` | VERSION | RO | `0x00010000` |
| `0x08` | LAYOUT | RO | `[7:0]` число конечных точек, `[15:8]` log2 размера слота |
| `0x0C` | DUT_ID | RO | CRC32 описания |
| `0x10` | DUT_CTRL | RW | `[0]` держать DUT в сбросе |
| `0x14`/`0x18` | CYCLES_LO/HI | RO | такты с момента снятия сброса; чтение LO фиксирует HI |

Конечная точка (слоты 1..N; нижняя половина окна — регистры, верхняя — буфер):

| Смещение | Регистр | Доступ | Содержимое |
|---|---|---|---|
| `0x00` | ID | RO | `0x4F435601` |
| `0x04` | VERSION | RO | `0x00020000` |
| `0x08` | GEOMETRY | RO | `[7:0]` слов в записи, `[15:8]` log2 глубины, `[23:16]` log2 шага слота, `[31:24]` log2 смещения буфера |
| `0x0C` | KIND | RO | `[7:0]` 1 = sink, 2 = source; `[8]` sink с backpressure; `[9]` lossless (DUT замораживается, пока буфер полон) |
| `0x10` | CTRL | RW | `[0]` enable, `[1]` clear (запись 1), `[2]` stall_en (sink) |
| `0x14` | STATUS | RO | sink: `[0]` full `[1]` overflow `[2]` enable `[3]` stall; source: `[0]` done `[2]` enable `[4]` active |
| `0x18` | COUNT | RO | sink: захвачено; source: отправлено |
| `0x1C` | DROPPED | RO | sink: потеряно при заполненном буфере |
| `0x20` | LENGTH | RW | source: сколько записей отправить (увеличение на ходу продолжает поток) |
| `0x24` | THROTTLE | RW | `[7:0]` вероятность паузы n/256 за такт |

**Самоописание.** Программе на PS нужен только базовый адрес хаба: число и размер слотов,
вид, ширина, глубина и раскладка каждой конечной точки читаются из регистров и сверяются с
метаданными. При любом несоответствии (другой `DUT_ID`, другая геометрия, не тот вид)
программа отказывается работать.

### 3.3. Модель ↔ прогонщик (C)
Модель ([ocv_model.h](../sw/include/ocv_model.h)) — четыре обратных вызова:
`configure` (опции `--model-opt k=v`), `reset`, `stimulus` (строит стимулы; может закончить их
раньше — например, когда загружена программа) и `input`. `input` получает каждую запись стимула
в порядке поступления в DUT и отвечает ожидаемыми записями выходных каналов (`emit`). Модель
вызывается **после** прогона DUT, поэтому через `observed()` может взять у DUT значения, которые
спецификация оставляет открытыми (показания таймеров), вместо того чтобы их маскировать. Поля
адресуются по именам (`ocv_get`, `ocv_set`), поэтому модель не зависит от раскладки битов. Прогонщик сравнивает по порядку и по полям с правилами
`exact / ignore / mask / abs / ulp` и при первом расхождении печатает канал, номер записи, поле,
оба значения и предыдущие записи.

## 4. Прогон

`ocv_runner` одинаков для всех DUT и для платы и косимуляции. На каждую пачку:
1. стимулы: генератор модели (или случайные поля), пока не кончатся или не заполнят пачку;
2. прогон: загрузка, запуск, ожидание, пока все source закончат, а выходы перестанут расти.
   Буфер монитора `lossless`, заполнившись, сливается в память PS (DUT в это время заморожен) и
   очищается — DUT продолжает; так захватывается поток любой длины;
3. модель: сброс, если сбрасывался DUT, затем все стимулы по порядку; ожидаемые записи;
4. проверка: потери, сверка по полям, число записей.

Следующая пачка идёт без сброса DUT (его состояние сохраняется), `--reset-each-batch` — со
сбросом. Прогон заканчивается после `--batches` пачек или когда у модели кончились стимулы.
Если не сравнено ни одной записи, прогонщик предупреждает (почти всегда это ошибка постановки).

Опции нагрузки: `--throttle-in P` (паузы стимулов), `--throttle-out P` (снятие ready на выходах).

## 4a. Реактивные DUT (обратная связь)

DUT, который сам просит данные (ведущее устройство шины, протокольный блок, процессор, обращающийся к
периферии), получает их через канал `stream`. Пока DUT работает, прогонщик на каждом опросе дочитывает
новые записи его выходных каналов и сразу отдаёт каждую модели (`react()`); ответы модели (`io->send()`)
идут в кольцевой буфер источника и доходят до DUT немедленно. С `freeze_when_starved` такт DUT стоит,
пока ответа нет, — DUT видит ответ на следующем своём такте, сколько бы процессор его ни готовил:

```
DUT: запрос ──► sink ──► PS: react() ──► send() ──► stream source ──► DUT: ответ
                                  такт DUT стоит, пока ответа нет (freeze_when_starved)
```

| Что | Как |
|---|---|
| когда включается | у модели есть `react()` или в описании есть `stream`-источник; модель работает в потоке прогонщика (`--overlap` не применяется) |
| кольцо источника | запись k — в слоте k mod depth, пишется, когда k < COUNT + depth; `LENGTH`, `COUNT` — 32-битные счётчики |
| задержка ответа | `--throttle-stream P`: ответы доходят до DUT с опозданием (вероятность P/256 на такт) — ошибки, которые проявляются только при медленной памяти, при нулевой задержке не видны |
| зависание | `--stall-polls N`: стимулы ждут, а ни один канал не двигается N опросов — `FAIL: DUT stalled` (например, DUT ждёт ответ на запрос, которого платформа не видела) |
| метрика | в итоговой строке — число ответов и время на ответ (время реакции процессора) |

Проверка: `hw/tb/tb_ocv_stream.sv` — с `FREEZE_STARVED` DUT ждёт ровно 1 свой такт при задержке
«процессора» 0–60 тактов, без него — 9–69; кольцо проходится многократно. Пример —
[examples/memsum](../examples/memsum/README.md).

## 4b. Слияние выходного потока (squash)

Выход, по которому ядро выдаёт запись почти каждый такт (поток выполненных инструкций процессора),
нагружает программу на PS сильнее всего: чтение записи и сравнение на каждое событие. Приём из
индустрии (DiffTest-H, MICRO'25) — сливать события в аппаратуре.

- **Аппаратура** (`ocv_sink`, `SQUASH = 1`, ключ `squash` в описании): на окно из N записей в буфер
  ложится одна — `{CRC32, CRC32C, число записей, последняя запись}`. Обе CRC идут по всем записям
  окна (сравниваемые биты: маска, которую программа задаёт перед запуском ядра регистрами
  `SQMASK_SEL`/`SQMASK`, флаг `KIND_SQMASK`; после сброса — маска из правил полей), поэтому меняются при любом отличии любой записи,
  даже если неверное значение позже перезаписано. Слитая запись выдаётся в такте последней записи
  окна, как обычная, — заморозка при полном буфере работает без изменений. Регистры: `SQUASH`
  (N), `TAKEN` (записей принято — прогресс, пока буфер растёт раз в окно), `CTRL.FLUSH` (выдать
  неполное окно в конце пакета).
- **Прерыватель окна** (`EP_REG_BRK_SEL`/`BRK_DATA`, `KIND_SQBRK`, 4 образца маска/значение): запись,
  совпавшая с включённым образцом, закрывает окно и становится его последней записью целиком — так
  программа получает значения, которые модель должна взять у ядра (таймеры, регистры устройств).
- **Программа:** прогонщик сливает записи модели так же (`ocv_squash_add`, на A72 — аппаратные
  инструкции `crc32cw`/`crc32w`) и сравнивает слитые записи. Модель не меняется.
- **Расхождение окна** уточняется повторным прогоном того же теста с `--squash 1`: прогон
  детерминирован (заморозка такта), поэтому ошибка находится на той же записи. Так же решается
  случай, когда модели нужны значения ядра (`observed()`, таймеры): со слиянием она их не видит,
  расхождение ведёт к повтору без слияния.
- Проверено: тестбенч `tb_ocv_squash` (окна 1/7/64, переполнения, маска сборки и маски, заданные во
  время работы, с обратным чтением); SCR1 в косимуляции —
  361 653 инструкции окном 256 и 4096; кампания неисправностей окном 256 находит все 5 ошибок на тех
  же инструкциях, что и без слияния.

## 4c. Выходы через DMA-кольца в памяти PS

Чтение буфера конечной точки по шине стоит на VD100 около 400 нс на слово: процессор читает окно устройства
по одному обращению за раз (`ocv_busbench`). Поэтому выходы можно собрать так, чтобы записи сами уходили в
память PS:

- **Аппаратура** (`ocv_gen.py --dma DW`, `ocv_sink` с `DMA = 1`, `ocv_dma_wr`, `ocv_axi_wr_arb`):
  - буфер выхода становится FIFO; `ocv_dma_wr` пакетами пишет записи через AXI4-master обёртки (`m_axi_*`,
    одна шина на все выходы, арбитр по пакетам, `AWID` = номер выхода) в кольцо в DDR;
  - запись k лежит по адресу `base + (k mod 2^RING_LOG2) * SLOT` (SLOT — шаг записи, не меньше ширины
    данных шины), нули добивают слот;
  - `RING_HEAD` растёт только по ответу записи (`BRESP`): данные уже в памяти. PS пишет `RING_TAIL`.
    Кольцо полно → FIFO полно → у выхода `lossless` такт DUT стоит, как при полном буфере: потерь нет;
  - пакеты INCR не длиннее 256 байт и не пересекают ни 256-байтную границу (значит, и 4 КиБ), ни конец кольца.
    Сброс DUT посреди пакета: пакет дописывается нулями, его ответ не считается.
- **Программа:**
  - `ocv_ring_setup` делит память DMA шины поровну между такими выходами (степени двойки, выровнены);
  - `ocv_ring_take` читает новые записи из памяти, перед этим делает `dc civac` по их строкам (путь NoC → DDR
    не когерентен кэшам A72), и сдвигает `RING_TAIL`;
  - прогонщик (`ocv_runner`) и UVM-слой (`ocv_uvm_dpi.c`) берут записи из кольца сами. Образ без DMA или PS без
    памяти DMA — прежний путь по шине. `--no-dma` — принудительно по шине.
- **Память на плате** (`ocv_bus_mmap_dma`): одна страница 2 МиБ (hugetlbfs; если пул пуст, программа
  резервирует страницу сама), иначе прозрачная huge page, иначе область `OCV_DMA_PHYS=<адрес>:<байт>` (например,
  отрезанная от Linux через `mem=`). Физический адрес — из `/proc/self/pagemap` (нужен root).
- **Ко-симуляция** (`OCV_GEN_FLAGS="--dma 128" sim/cosim.sh ...`): «память PS» — массив в программе
  ко-симуляции, ведомый AXI4 со случайными `AWREADY/WREADY` (`--dma-ready P`) и опаздывающими ответами
  (`--dma-bdelay N`).
- **Проверено:**
  - `hw/tb/tb_ocv_dma.sv` на 7 геометриях (запись 32–640 бит, шина 64–512 бит, кольцо меньше блока и больше
    FIFO): порядок, целостность и нули добивки, полное кольцо, заморозка DUT, сброс посреди пакета, режим без
    кольца. 6 внесённых ошибок `ocv_dma_wr` ловятся;
  - ко-симуляция mac16, SCR1 (dhrystone, случайная программа со свёрткой 256), memsum (реактивный),
    CV32E40P (10 каналов): PASS;
  - кампания ошибок SCR1 через DMA находит те же 5 ошибок на тех же командах.
- **Не проверено:** сборка Vivado (порт `ocv_dma` блок-дизайна → `S06_AXI` NoC → DDR) и прогон на плате.

## 5. Правила переносимости

1. На стыке с PS — AXI4-Lite для управления и, по желанию, AXI4-master для DMA-колец (`m_axi_*`). AXI4 есть на
   любой SoC-ПЛИС (Zynq HP/ACP, MPSoC HP/HPC, Versal NoC); никаких зависимостей от CIPS/NoC/PS7/PS8 внутри
   `hw/`.
2. Память — только выводом из RTL, без генераторов конкретного семейства.
3. Всё, что зависит от платы, — только в `platforms/<плата>/`.
4. Программа на PS — C99 без внешних зависимостей.
5. Базовый адрес — параметр запуска, а не константа в коде.

Сейчас собираем и проверяем только под Versal (ALINX VD100).

`test_all.sh` — полная регрессия без платы:

| Шаг | Что проверяет |
|---|---|
| контракт регистров | все константы SV-пакета и C-заголовка совпадают |

| генератор | 9 видов неверных описаний отвергаются с указанием места ошибки |
| косимуляция mac16 | тот же C-код, что на плате, против Verilator-модели: `--info`, обычный прогон, с паузами и случайными задержками AXI, со сбросом каждой пачки |
| кампания неисправностей mac16 | 13 внесённых ошибок в IP, исход каждой совпадает с ожидаемым |
| SCR1 | `hello`, dhrystone и случайная программа через OCV с монитором `lossless` (сливы буфера) |
| кампания неисправностей SCR1 | 5 ошибок в АЛУ ядра на случайной программе — все найдены |
| мост VD100 (`BRIDGE=1`, нужен Vivado) | настоящий SmartConnect платформы + mac16, программа PS через DPI: `--info` и полный прогон со случайными задержками ведущего |

Способность тестбенча ядра находить ошибки проверена мутациями RTL (перестановка данных,
счётчики, clear, stall, backpressure, мультиплексор хаба, сброс DUT, протокол AXI, правило
AXI-Stream при паузах) — все пойманы.

### SCR1 (косимуляция)

| Программа | Инструкций сверено | Сливов буфера (4096) |
|---|---|---|
| `hello` | 9 610 | 2 |
| `dhrystone21` (самоизмеряющий, счётчики тактов из DUT) | 164 891 | 40 |
| случайная RV32IM, 4000 операций × 10 | 35 936 | 8 |

Пять ошибок в АЛУ ядра (`sra` как `srl`, сдвиг на 1, `bge` без переполнения, `bgeu` при
`op2 = 0xFFFFFFFF`, `mulhu` как `mulhsu`): `hello` и dhrystone не находят ни одной — они не
задевают эти случаи; случайная программа с граничными значениями находит все пять, каждую — с
номером инструкции, `pc` и полем. Мутация платформы «монитор `lossless` не замораживает DUT»
ловится на SCR1 как расхождение ровно на записи 4096 (переполнение буфера).
