# Пути улучшения OCV: по подсистемам, с конкретикой

Дополнение к [SOTA_PLAN.md](SOTA_PLAN.md) (анализ конкурентов и план до конференции). Здесь —
инженерная конкретика: какие элементы улучшать, как и в каком порядке, с указанием файлов.
Основа — код репозитория и выводы литературного слива (research_notes.md §11–12).

Условные обозначения приоритета: **[P1]** делать в первую очередь (влияет на клэймы статьи),
**[P2]** заметно улучшает, **[P3]** по остаточному принципу / опционально.

## 1. Эталонные модели (`models/cpu`) — сердце производительности

Текущее состояние: `rv32_fast.c` (предекодирующий интерпретатор, 48 нс/ком на ПК) и `rv32_jit.c`
(JIT RV32IMC→AArch64, ~30 нс чистого кода на A72, по умолчанию на aarch64), кросс-чек обоих против
`iss` (`t_fast.c`), Spike как полный эталон (56/56 riscv_isa). Профиль платы: модель 91–94% времени
длинных прогонов, изнутри неё: свёртка/CRC 32%, раздача jit_step 19%, board_ref 15%, сам JIT 10%.

### 1.1. Снять обвязку вокруг модели [P1] — самый большой запас скорости

Цель: ≤100 нс/команду сверх исполняемого кода модели → ARM ≥10 млн сверенных команд/с.

- **Свёртка на месте при DMA.** Сейчас 32% времени — две CRC по каждой записи окна. С DMA-кольцами
  записи приходят почти бесплатно → сравнивать 16–24 байта записи напрямую (mismatch виден сразу,
  без повтора окна). Реализация: путь в `ocv_runner.c`/`ocv_cpu_model.c`: при `--dma` и окне N
  сравнивать записи модели и кольца memcmp-блоком, свёртку оставить опцией (`--squash` для
  ПЛИС→ПК-канала и очень широких записей). Выбрать по замеру — план уже есть в review_and_plan §4.2.
- **Раздача `jit_step` (19%) → записи из переведённого кода.** JIT уже пишет динамические результаты
  (`jout_t`), статическая часть (`jins_t`) — таблица. Убрать промежуточную сборку записей
  через `cpu_retire_t` в общем цикле: формирование записи окна — прямо в цикле по `jout_t`/`jins_t`
  (раскладка полей известна на этапе компиляции — `CPU_FOR_STREAMS`, `cpu_stream_field`, см. как
  сделано в стендовой сборке `hw/cpu/run.sh <bind> bench`, где 110→48 нс). Перенести ту же технику
  в UVM-путь (движок A) и в прогонщик.
- **`board_ref` (15%) → та же постоянная раскладка**, что уже сделана для стенда (п. 6б.9):
  поля по индексам, не по именам строк.
- **Второе ядро A72.** Два режима, выбрать по замеру: (а) конвейер — ядро 0 исполняет модель,
  ядро 1 сверяет/готовит стимулы (при `--overlap` уже есть поток модели — довести до пиннинга
  `pthread_setaffinity_np`); (б) две копии DUT в ПЛИС (ресурсов хватает: CVA6 ~10.5k LUT из 150k,
  каждая со своей моделью — ×2 на регрессии независимых программ). Режим (б) идейно = ISAAC
  (отозвана, но идея жива); реализуется клоном конечных точек в `gen/cpu_wrap.py` + вторым
  экземпляром модели в прогонщике.

### 1.2. Верификация самого эталона [P1] — «насколько золот ваш золотой»

Рецензент DiffTest-жанра спросит про доверие к модели (прецедент: MachCSL нашёл баги в самом
Sail; ChatFuzz — расхождения в Spike). Ответ из трёх слоёв, все частично есть:

- **Дифференциальный фаззинг JIT↔интерпретатор↔Spike на случайных программах** — уже есть
  (`t_fast.c` + кампания из 7 внесённых ошибок JIT, все пойманы). Оформить как регулярную
  кампанию в `test_all.sh` с генератором случайных программ (сейчас тест фикссированный
  `jitcheck.S`): N случайных программ, все три модели, попарное сравнение по каждой записи.
- **Spike на плате**: собрать под aarch64 (`tools/get_spike.sh` + `g++-aarch64-linux-gnu`) и
  прогнать riscv_isa на A72 — закрыть пункт ROADMAP §7. Spike не для скорости: он арбитр при
  расхождении DUT↔JIT (повтор окна на ПК) и запасной путь для того, чего JIT не умеет.
- **Третий оракул — sail-riscv [P2]**: официальный golden model, собрать под x86 на ПК, гонять
  в роли арбитра на расхождениях. В статье — аргумент мульти-оракульности против
  «а вдруг ваш профиль модели не по спецификации» (наша история: MPP после сброса CVA6 — ошибка
  именно профиля, а не ядра).

### 1.3. Расширения модели [P2–P3]

- **Профили ядер автоматически** (закрыть T1-хвост «ручная работа под DUT»). Сейчас `:cv32e40p`
  и `:cva6` — таблицы CSR/исключений, написанные по RTL. Путь: выводить профиль из готовой
  конфигурации верификатора (настройки riscv-dv/ISS в тестбенче) или из тестов `riscv-arch-test`
  (запустить ACT — что не сошлось, то и отличается профиль). Значения, оставленные реализации,
  уже берутся через `observed()` — это правильный механизм, расширить на CSR-таблицы.
- **RV64 / A-F-D расширения [P3]**: только если появится ядро-носитель; для статьи не нужно.
  Сейчас честная граница: RV32IMC + Zicsr (+ прерывания MTI/MEI для CVA6).
- **`cpu_step_n` (пакетный интерфейс)** — замерен, выигрыша нет; оставить как есть (документировано).

## 2. Транспорт ПЛИС→PS (`hw/rtl`, `platforms/vd100`) [P1 для замеров, P2 для фич]

Текущее: PIO ~400 нс/слово (M_AXI_LPD → SmartConnect), DMA-кольца `ocv_dma_wr` через `S06_AXI`
NoC → DDR (128 бит), hugepage + `dc civac` на ARM. С 13–14.10 DMA на плате подтверждён.

- **HEAD в памяти [P2, дёшево]**: ARM опрашивает HEAD PIO-чтением (~400 нс). Записывать HEAD и в
  кольцо (последний слот / отдельная строка) — ARM читает из DDR по кэшу. Важно для реактивного
  режима и опроса. Уже в плане (review_and_plan §6б).
- **Когерентный путь [P2]**: сейчас `dc civac` после NoC. Вариант ACP/ACE-Lite (на Versal —
  через NoC к CIPS DCache-coherent порт) убрал бы инвалидации. Замерить оба, оставить лучший;
  контракт `ocv_ring_*` не меняется.
- **Полоса**: замерить предельную полосу DMA-кольца (сейчас не измерена явно) — для таблицы T5
  и сравнения с PCAP FERIVer (140 МБ/с) и трафиком DiffTest-H.
- **Ширина 256/512 бит [P3]**: `DW` параметризован; упрётся в NoC, сначала замер.

## 3. UVM-слой (`uvm/`) — главный клэйм, доводить до безупречности [P1]

Текущее: 5 путей (A–E2, docs/UVM.md), переведённый SCR1 ×4–73, core-v-verif тест 1 на плате
×1.4–165 (coremark), встроенный решатель ×130 к z3, воспроизведение ошибки → VCD на ПК.

- **3.1. Виртуальная периферия core-v-verif в ПЛИС [P1, нужен день с платой]** — главный тормоз
  теста 1 на плате (dhrystone медленнее coremark при ×18 меньше команд: каждая печать — цикл
  в ARM-тестбенч). План уже есть (FOREIGN_TB_CV32E40P «вариант 2»): printer/status/timer как
  окна устройств обёртки (механизм `device` в cpu_wrap уже есть, у CVA6-привязки так и сделано).
  Копия агентов `uvma_obi_memory` (библиотечные, общие для OpenHW) — обращения ядра к 0x1000_0000/
  0x15000000/0x20000000 уходят в ПЛИС, до тестбенча доходит только редкое. Замер «до/после»
  включить в docs/UVM.md §3.4.
- **3.2. `randomize()` на ARM [P1 для mac16-границы]**: остаток ~60 мкс/вызов — подготовка вызова
  в коде Verilator (VlRandomizer создание/копирование, строки, write_var), не наш решатель.
  Путь: (а) патч Verilator — кэш объекта рандомайзера по точке вызова (у нас уже 3 патча
  Verilator — `ocv_lazy_constraint_lines`, `ocv_tb_compat`, `ocv_fast_random`; следующий в тот же
  ряд); (б) если не успеем — честная граница mac16 ×0.5 с профилем (уже есть) и объяснением
  (закон Амдала: тестбенч — узкое место, DVCon-классика).
- **3.3. Покрытие covergroup «по изменению» [P2]**: план в docs/UVM.md §6.3 — FPGA присылает запись
  при изменении отслеживаемых сигналов (поток `watch` в cpu_wrap уже есть!), бины те же,
  отличаются только счётчики повторов. Реализовать на SCR1 r2 (сборщик покрытия уже проверен
  бит-в-бит). Это закрывает допущение «потактовое покрытие не вычисляется» и усиливает клэйм
  «покрытие полное».
- **3.4. Verilator-патчи → upstream [P2, высокая ценность/низкая стоимость]**: проверить каждый из
  наших патчей на Verilator 5.052+ (UVM 2020-3.2): что уже не нужно — выпороть; что нужно —
  оформить PR (кандидаты: `t_cg_method.sv` — вызов covergroup-метода через внешний объект по
  IEEE 1800-2023 19.4; `t_rand_null_member.sv` — randomize по пустому указателю по 18.5.9;
  lazy constraint lines — перфоманс). PR в Verilator = вклад сам по себе + исчезает форк.
- **3.5. `dist`-веса [P3]**: Verilator игнорирует веса — либо патч, либо документированное
  ограничение (сейчас второе, правильно).

## 4. Генерация по покрытию и стимулы [P1 для таблиц, P2 для фич]

Текущее: `cv32_gen.c`/`scr1_gen.c` (по ISA), `cv32_cov.c`/`scr1_cov.c` (1693/1695/1478 бинов),
directed-режим на непокрытые бины, 100% за 4–6 программ.

- **4.1. Кривые сходимости [P1]**: снять «бины против времени» для случайной vs directed на всех
  трёх ядрах, на плате и на ПК. Ответ на критику SimFuzz (покрытие плато и смещено): показать,
  где наши бины насыщаются, и что directed закрывает хвост за минуты. Для сравнения с
  TurboFuzz (×2.23 покрытие) и LyraGen — хотя бы качественная позиция: их метрика — фаззинг-
  coverage (регистры/ветвления), наша — семантические ISA-бины; указать различие явно.
- **4.2. Скорость генератора [P1, замер]**: инструкций/с нашего генератора против riscv-dv на SV
  (~10k) и eUVM (~1M). Наш работает на ARM во время прогона — если ≥100k инстр/с, в паре с
  платой это «генерация не узкое место»; если меньше — перенести генерацию на ПК (сценарий
  допускает, канала GbE хватит: программа = килобайты).
- **4.3. Класс событий прерываний/CSR [P2]**: урок #3175 — события вокруг `mie`/`mip`/ловушек —
  богатый источник реальных багов. Добавить в покрытие бины «запись mie → прерывание через k
  команд» (k=0..N), «ловушка → первая загрузка в обработчике», «невыровненная загрузка →
  следующая загрузка» (именно эти паттерны нашли наши баги). В генератор — направленные
  последовательности таких событий.
- **4.4. LLM-режим генерации [P3, отдельная фича]**: слой «LLM-сидов» над генератором
  (ChatFuzz/LyraGen-линия): LLM предлагает программу-кандидата по описанию непокрытых бинов,
  генератор валидирует и исполняет. Модно, дёшево как надстройка, но не блокер статьи.

## 5. Обёртка ядра (`hw/cpu`, `gen/cpu_wrap.py`) [P2]

Текущее: `.bind`-файл описывает ядро (шины OBI/AXI, память, устройства, входы, потоки), RTL ядра
не меняется; 3 ядра подключены. Оценка: подключение CVA6 потребовало ~50 строк привязки + 54
строки оболочки портов + профиль модели.

- **5.1. Стандартизовать путь RVFI/RVVI [P2]**: у CVA6 поток из родного RVFI (`cva6_rvfi.sv`);
  у CV32E40P — сигналы трассировщика; у SCR1 — свой RVFI-lite. Сделать «rvfi-профиль» в
  cpu_wrap: `stream`-директивы генерируются из стандартных имён `rvfi_*`, для ядер с RVFI
  привязка сокращается до строк `bus/memory/model`. RVVI (riscv-verification/RVVI) —
  roadmap-абзац + adapter по мере стандартизации.
- **5.2. Четвёртое ядро для доказательства универсальности [P2]**: Ibex (RV32IMC, есть RVFI,
  LowRISC) — самый дешёвый кандидат: привязка через rvfi-профиль из 5.1, модель `:ibex`
  (профиль машинного режима). Доказывает «два ядра — не случайность» (рецензентский пункт «DUT
  too small / ad hoc»).
- **5.3. Прерыватели окна для таймерных CSR SCR1 [P2, мелочь]**: ложное расхождение dhrystone при
  окне 64 (review_and_plan 6б.9) — сделать `stream ... brk` на чтениях mcycle/mtime, как у
  CVA6-привязки.

## 6. Отладка и диагностика [P2]

- **6.1. VCD с платы для `hw/cpu` [P1, дёшево]**: у UVM-пути есть (`+OCV_WAVE`, `tbwave.py`), у
  прогонщика — нет. Сделать `run.sh wave <программа> <канал>:<запись>` для cosim-пути
  (стимулы детерминированы, повтор в Verilator тривиален). Это же закрывает п. 6б.3 —
  «неподтверждённые баги CVA6 нужно разобрать по временной диаграмме»: flushed_load_min и
  stale_load_min получить VCD (PCI-ассерты hpdcache уже указывают «bad SIZE»), подтвердить/опровергнуть
  ядро. Для статьи критично: два «кандидата» должны получить статус.
- **6.2. Метрика «время от бага до волны» [P2]**: замерить (плата находит запись N за секунды →
  ПК строит VCD за минуты) — включить в таблицу T1 как отладочную метрику (у FERIVer это
  главный аргумент, у нас должно быть не хуже).
- **6.3. Снапшоты длинных прогонов [P3]**: LightSSS-стиль (fork-снапшоты — на ARM не работает,
  но периодический журнал стимулов + чекпойнт модели = дешёвый эквивалент). У нас детерминизм
  freeze уже даёт повтор с нуля — посчитать, хватает ли (407 млн команд × 48 нс = повтор ~20 с
  на ПК — вероятно, хватает, задокументировать как ответ).

## 9. Что НЕ делать (проверенные тупики и осознанные границы)

- Повышение частоты A72 / перенастройка Linux — решение пользователя: штатный образ, как есть.
- `cpu_step_n` пакетный интерфейс модели — замерен, выигрыша нет.
- UVM на ПК + ARM как транспорт (классическая коэмуляция) — отвергнуто, есть готовые решения.
- Подписи, посчитанные заранее на ПК — не вписывается в сценарий «компьютер не нужен».
- dhrystone/coremark как метрики проекта — метрики: сгенерированные тесты, покрытие, время до
  бага (решение пользователя 13.10).
